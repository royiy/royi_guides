מדריך זה מרכז שאלות ראיון מכל התחומים שסקרנו במדריכים 1-9, ברמת קושי עולה, לצד תשובות תמציתיות. מומלץ לעבור על המדריכים הקודמים לפני שקוראים כאן - כאן זה בעיקר ריכוז וחזרה.

## חלק א': שאלות יסוד (Junior)

<details class="qa">
<summary>1. מה זה API?</summary>

ממשק שמאפשר לתוכנות שונות לתקשר זו עם זו, ע"י הגדרת חוזה ברור (אילו בקשות אפשר לשלוח, אילו תשובות יתקבלו).

</details>

<details class="qa">
<summary>2. מה זה REST?</summary>

סגנון ארכיטקטוני ל-Web APIs, מבוסס על עקרונות: Client-Server, Statelessness, Cacheability, Uniform Interface, Layered System.

</details>

<details class="qa">
<summary>3. מה ההבדל בין GET ל-POST?</summary>

GET מיועד לקריאת נתונים בלבד (Safe, Idempotent, בלי body בבקשה). POST מיועד ליצירת משאב חדש/שינוי מצב (לא Safe, לא Idempotent, יש body).

</details>

<details class="qa">
<summary>4. מה זה JSON, ולמה הוא כל כך נפוץ ב-APIs?</summary>

JavaScript Object Notation - פורמט חילופי נתונים קליל, קריא לבני אדם, ונתמך כמעט בכל שפת תכנות. פשוט יותר מ-XML וקל יותר לפרסור.

</details>

<details class="qa">
<summary>5. מה ההבדל בין 401 ל-403?</summary>

401 = לא מזוהה בכלל ("מי אתה?"). 403 = מזוהה, אבל אין הרשאה ("אתה לא רשאי").

</details>

<details class="qa">
<summary>6. מה זה Endpoint?</summary>

כתובת URL ספציפית ב-API שמייצגת פעולה או משאב, למשל `GET /users/42`.

</details>

<details class="qa">
<summary>7. מה זה Query Parameter, ומה ההבדל מ-Path Parameter?</summary>

Path Parameter הוא חלק מהנתיב עצמו וממוקד במשאב ספציפי (`/users/42` - ה-42 הוא path param). Query Parameter מגיע אחרי `?` ומשמש בעיקר לסינון/מיון/pagination (`/users?role=admin`).

</details>

## חלק ב': שאלות ברמה בינונית (Mid-Level)

<details class="qa">
<summary>8. מה זה Idempotency, ואילו HTTP Methods הם Idempotent?</summary>

פעולה שביצוע חוזר שלה נותן את אותה תוצאה כמו ביצוע יחיד. GET, PUT, DELETE, HEAD הם Idempotent. POST לא (בד"כ).

</details>

<details class="qa">
<summary>9. תארו את זרימת האימות עם JWT מקצה לקצה.</summary>

1) המשתמש שולח credentials (username/password) ל-endpoint של login
2) השרת מוודא ומחזיר JWT חתום עם expiration
3) הלקוח שומר את הטוקן (לרוב ב-memory או secure storage) ושולח אותו ב-Header `Authorization: Bearer <token>` בכל בקשה עוקבת
4) השרת מוודא את החתימה ואת התוקף בכל בקשה, בלי לשמור state

</details>

<details class="qa">
<summary>10. איך הייתם מעצבים endpoint ל-Pagination? מה ההבדל בין page-based ל-cursor-based?</summary>

`GET /items?page=2&per_page=20` (page-based, פשוט אך בעייתי בדאטה משתנה) לעומת `GET /items?cursor=xyz&limit=20` (cursor-based, יציב יותר לדאטה דינמי).

</details>

<details class="qa">
<summary>11. מהם 3 עקרונות REST שאתם יכולים להסביר לעומק?</summary>

בחרו 3 מתוך: Client-Server, Statelessness, Cacheability, Uniform Interface, Layered System, Code on Demand - והכינו הסבר של 2-3 משפטים לכל אחד + דוגמה.

</details>

<details class="qa">
<summary>12. מה זה CORS ולמה דפדפנים חוסמים בקשות Cross-Origin?</summary>

מדיניות אבטחה של דפדפנים שמונעת מדף web לשלוח בקשות (במיוחד עם credentials) לדומיין אחר בלי אישור מפורש (Headers כמו `Access-Control-Allow-Origin`) מהשרת היעד - מונע התקפות כמו CSRF.

</details>

<details class="qa">
<summary>13. מה זה Rate Limiting ואיך הייתם מיישמים אותו?</summary>

הגבלת מספר בקשות ללקוח בפרק זמן נתון. מימוש נפוץ: middleware שסופר בקשות ב-Redis לפי IP/API Key, ומחזיר `429` כשחורגים מהמכסה, עם Header `Retry-After`.

</details>

<details class="qa">
<summary>14. מה ההבדל בין PUT ל-PATCH?</summary>

PUT מחליף את כל המשאב (עדכון מלא, כל השדות). PATCH מעדכן רק את השדות שסופקו (עדכון חלקי).

</details>

<details class="qa">
<summary>15. מה זה Webhook, ובמה הוא שונה מ-API רגיל?</summary>

API רגיל: הלקוח **מבקש** מידע מהשרת (Pull). Webhook: השרת **שולח** מידע ללקוח כשמתרחש אירוע מסוים (Push) - למשל, Stripe שולח webhook כשתשלום הצליח.

```javascript
// דוגמת endpoint שמקבל webhook מ-Stripe
app.post("/webhooks/stripe", express.raw({type: "application/json"}), (req, res) => {
  const event = stripe.webhooks.constructEvent(
    req.body, req.headers["stripe-signature"], process.env.STRIPE_WEBHOOK_SECRET
  );
  if (event.type === "payment_intent.succeeded") {
    // עדכון סטטוס הזמנה ב-DB
  }
  res.json({ received: true });
});
```

</details>

## חלק ג': שאלות מתקדמות (Senior)

<details class="qa">
<summary>16. איך הייתם מעצבים API שצריך לתמוך במיליוני משתמשים? אילו שיקולים חשובים?</summary>

נקודות מפתח לדיון: Statelessness לצורך horizontal scaling, caching בכל שכבה (CDN, Redis, HTTP), Rate Limiting למניעת abuse, database indexing ו-read replicas, API Gateway למרכוז concerns (auth, logging, rate limiting), async processing לפעולות כבדות (queues), ו-monitoring/alerting.

</details>

<details class="qa">
<summary>17. מה זה Circuit Breaker Pattern, ולמה הוא רלוונטי ל-API calls בין מיקרו-שירותים?</summary>

דפוס עיצוב שמונע קריאות חוזרות לשירות שכבר נכשל, כדי למנוע "אפקט דומינו" (cascading failures). אחרי X כשלונות רצופים, ה-Circuit "נפתח" וחוסם קריאות זמנית, ואז בודק תקופתית אם השירות התאושש (Half-Open state).

</details>

<details class="qa">
<summary>18. מה ההבדל בין Synchronous ל-Asynchronous API design, ומתי נבחר כל אחד?</summary>

Synchronous - הלקוח מחכה לתשובה מיידית (מתאים לפעולות מהירות). Asynchronous - השרת מחזיר מיד `202 Accepted` עם מזהה job, והלקוח בודק סטטוס בנפרד או מקבל webhook כשהעבודה מסתיימת (מתאים לעיבוד כבד - יצירת דוח, עיבוד וידאו וכו').

```
POST /reports          → 202 Accepted { "job_id": "abc123", "status_url": "/jobs/abc123" }
GET /jobs/abc123        → { "status": "processing" } / { "status": "completed", "result_url": "..." }
```

</details>

<details class="qa">
<summary>19. איך הייתם מטמיעים Multi-Tenancy ב-API (כלומר, API שמשרת כמה לקוחות/ארגונים)?</summary>

אפשרויות: (א) DB נפרד לכל tenant (בידוד מקסימלי, יקר יותר), (ב) schema נפרד באותו DB, (ג) שורה משותפת עם `tenant_id` בכל טבלה (הכי נפוץ, דורש הקפדה על סינון ב-**כל** שאילתה כדי למנוע דליפת מידע בין ארגונים).

</details>

<details class="qa">
<summary>20. מהי הגישה הנכונה לטיפול בשגיאות חלקיות ב-batch operations?</summary>

למשל `POST /users/bulk` שיוצר 100 משתמשים ו-3 נכשלים - מומלץ להחזיר `207 Multi-Status` עם פירוט תוצאה לכל פריט בנפרד, ולא להיכשל/להצליח הכל-או-כלום (אלא אם יש דרישה עסקית ל-atomicity).

</details>

<details class="qa">
<summary>21. איך הייתם מנטרים (monitoring) API בייצור?</summary>

מדדים מרכזיים (Golden Signals): **Latency** (זמן תגובה, כולל p50/p95/p99), **Traffic** (בקשות לשנייה), **Errors** (אחוז 4xx/5xx), **Saturation** (עומס על משאבים - CPU/זיכרון/connections). כלים: Prometheus + Grafana, Datadog, New Relic. חשוב גם Distributed Tracing (Jaeger, OpenTelemetry) במיקרו-שירותים.

</details>

<details class="qa">
<summary>22. מה ההבדל בין API Gateway ל-Load Balancer?</summary>

Load Balancer מפזר תעבורה בין מספר instances של אותו שירות (Layer 4/7). API Gateway עושה זאת גם, אבל מוסיף concerns נוספים ברמת ה-API: אימות מרכזי, Rate Limiting, טרנספורמציית בקשות/תשובות, ניתוב ל-microservices שונים לפי path, ולעיתים אגרגציה של כמה קריאות ל-Response אחד.

</details>

## תרגיל מעשי נפוץ בראיונות: "עצבו API ל-X"

דוגמה: "עצבו API למערכת הזמנת מסעדות". גישה מומלצת לתשובה:

```
1. זהו את המשאבים (Resources): Restaurants, Tables, Reservations, Users
2. הגדירו endpoints בסיסיים:
   GET    /restaurants
   GET    /restaurants/{id}
   GET    /restaurants/{id}/availability?date=2026-08-20&party_size=4
   POST   /reservations
   GET    /reservations/{id}
   DELETE /reservations/{id}      (ביטול)
3. חשבו על edge cases: מה קורה אם שני משתמשים מזמינים את אותו שולחן באותו רגע? (concurrency - locking/optimistic locking)
4. דונו באימות (מי יכול להזמין? האם צריך להיות מחובר?)
5. דונו ב-rate limiting (למנוע spam הזמנות)
6. דונו ב-notifications (webhook/email כשההזמנה מאושרת)
```

זו לא "שאלה עם תשובה אחת נכונה" - המראיינים בודקים תהליך חשיבה, לא רק תוצר סופי.

## טיפים כלליים להצלחה בראיון API

- 💡 **תמיד תנו דוגמה קונקרטית** - במקום "REST הוא stateless", תגידו "REST הוא stateless, כלומר כל בקשה כמו GET /orders/42 חייבת לכלול את כל המידע הדרוש (למשל טוקן אימות), השרת לא זוכר את הבקשה הקודמת".
- 💡 **אם לא יודעים תשובה - תגידו "אני לא בטוח, אבל הייתי מנחש ש..."** - מראיינים מעריכים כנות ותהליך חשיבה, יותר מתשובה שגויה בביטחון.
- 💡 **התאמנו לתאר trade-offs**, לא רק "מה נכון". כמעט כל שאלת עיצוב API היא trade-off (REST vs GraphQL, page vs cursor pagination וכו') - הראו שאתם מבינים את שני הצדדים.
- 💡 **הכינו סיפור אחד או שניים מניסיון אמיתי** (גם מפרויקט אישי) שבו נתקלתם באתגר קשור ל-API (bug של authentication, בעיית ביצועים שפתרתם עם caching וכו').
- 💡 **תרגלו לצייר תרשים זרימה** (OAuth, request lifecycle) על לוח/נייר - הרבה ראיונות כוללים whiteboarding.
- ⚠️ אל תשננו הגדרות בלי להבין - מראיינים מנוסים שואלים "למה" ו"תנו דוגמה" ומזהים שינון מיד.

## רשימת בדיקה מהירה לפני ראיון (Checklist)

- [ ] יודע להסביר REST ו-6 העקרונות שלו עם דוגמאות
- [ ] יודע את ההבדל בין כל HTTP Methods, ומהו idempotent/safe
- [ ] יודע 10-15 status codes בעל פה ומתי כל אחד רלוונטי
- [ ] יודע להסביר JWT, OAuth 2.0, ואת ההבדל מ-session auth
- [ ] מכיר את OWASP API Security Top 10 ברמה בסיסית
- [ ] יודע להסביר Versioning, Pagination, ו-Rate Limiting עם דוגמאות קוד
- [ ] יודע להשוות REST ל-GraphQL וגם ל-gRPC/WebSockets ברמה כללית
- [ ] יודע לדבר על Testing (unit/integration/load) ו-Monitoring
- [ ] מוכן עם דוגמה/סיפור אישי מניסיון מעשי
