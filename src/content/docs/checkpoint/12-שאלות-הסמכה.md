מבחן אינטראקטיבי ברמת קושי גבוהה, בסגנון שאלות הסמכת **Check Point Certified Security Administrator/Expert (CCSA/CCSE)** - בניגוד למבחן החזרה הכללי בפרק הקודם, כאן כל שאלה בודקת נקודה עדינה ומטעה שדורשת הבנה אמיתית של מנגנוני הפנים של Check Point (SIC, ClusterXL, Policy Install, CoreXL ועוד), לא רק שינון. בחרו תשובה ותקבלו מיד משוב עם הסבר מפורט.

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>1. מה קורה בפועל כאשר ה-SIC בין Security Gateway ל-Security Management Server נשבר (למשל תעודה שפגה או Trust שהתקלקל), ומהי הדרך הנכונה לתקן זאת?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין דרך לתקן - חובה להתקין את הגייטווי מחדש מאפס ולאבד את כל הקונפיגורציה המקומית</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. מבצעים Reset SIC בגייטווי (<code>cpconfig</code> -&gt; Secure Internal Communication -&gt; Reset) שמייצר Activation Key חדש (One-Time Password), ואז ב-SmartConsole על אובייקט הגייטווי לוחצים Communication -&gt; Reset ומזינים את אותו Activation Key כדי לבסס מחדש את האמון; חשוב לזכור שבזמן שה-SIC שבור, המדיניות שכבר מותקנת על הגייטווי ממשיכה לאכוף כרגיל - רק לא ניתן לדחוף מדיניות חדשה או למשוך לוגים</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. די להפעיל את הגייטווי מחדש (Reboot) וה-SIC יתאחה אוטומטית ללא כל פעולה נוספת</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. יש לשנות את כתובת ה-IP של הגייטווי כדי לאלץ את המערכת ליצור SIC חדש</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> SIC נשען על תעודות SSL הדדיות בין ה-Gateway ל-SMS. כשהאמון מתקלקל (שעון לא מסונכרן, תעודה שפגה, שינוי לא תקין), הפתרון הוא Reset SIC - יצירת Activation Key חדש בגייטווי דרך <code>cpconfig</code>, ואז ביסוס מחדש של האמון באובייקט הגייטווי ב-SmartConsole עם אותו Activation Key. נקודה שרבים מפספסים: שבירת SIC לא הופכת את הגייטווי ל"עיוור" - הוא ממשיך לאכוף את המדיניות האחרונה שהותקנה עליו כרגיל, כי האכיפה בפועל מתבצעת ב-Kernel של הגייטווי ולא תלויה בחיבור חי ל-Management. הבעיה היא רק שאי אפשר לדחוף שינויי מדיניות או לרכז לוגים עד שהאמון יתוקן.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>2. ב-ClusterXL Load Sharing Mode, כששני חברי הקלאסטר פעילים בו-זמנית ומחלקים ביניהם תעבורה, מה עדיין חייב להתקיים ברקע כדי ש-Failover יהיה תקין בלי לאבד חיבורים קיימים?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין צורך בשום דבר נוסף - כל חבר מנהל טבלת חיבורים נפרדת משלו, וזה מספיק בכל מקרה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. חובה ששני החברים ירוצו תמיד עם אותו Hardware בדיוק, ואין קשר לטבלת החיבורים</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. חייב להתקיים סנכרון State (טבלת Connections/State) שוטף בין חברי הקלאסטר דרך רשת ה-Sync הייעודית - כך שגם חבר שלא טיפל בחיבור מסוים מודע אליו, ויכול "לאמץ" אותו במקרה של Failover בלי לנתק אותו</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Load Sharing Mode לא תומך כלל ב-Stateful Failover, ולכן כל חיבור קיים תמיד ננתק במעבר בין חברים</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> גם ב-HA וגם ב-Load Sharing, ClusterXL מבוסס על סנכרון State שוטף בין החברים דרך רשת/ממשק Sync ייעודי. כך, גם כשחבר מסוים לא היה זה שטיפל בחיבור מסוים (במיוחד רלוונטי ב-Load Sharing שבו שני החברים פעילים), הוא עדיין מודע למצב החיבור, ויכול להמשיך לטפל בו בצורה חלקה אם החבר האחר נופל. בלי הסנכרון הזה, כל Failover היה גורם לניתוק מסיבי של חיבורים קיימים, בין אם במצב HA ובין אם ב-Load Sharing.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>3. מה בפועל קורה בגייטווי במהלך תהליך Install Policy, ומדוע חיבורים קיימים שכבר אושרו בדרך כלל לא ננתקים?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. ה-Management שולח לגייטווי את קובצי המדיניות בשפה קריאה לאדם, וכל חבילה מתורגמת "תוך כדי תנועה" ברגע שהיא עוברת</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. ה-Management מבצע Compile למדיניות (מהגדרות ברמת ה-Rule Base ל-Inspection Code בינארי), מעביר אותה לגייטווי, וזה טוען אותה ל-Kernel כמדיניות חדשה; חיבורים קיימים שכבר נבדקו ואושרו נשארים רשומים בטבלת ה-Connections הפעילה, ולכן ממשיכים לעבור לפי אותה רשומה קיימת בלי להיבדק מחדש מול הרשימה החדשה של הכללים</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. הגייטווי חוסם את כל התעבורה לחלוטין (Downtime מלא) עד לסיום תהליך ההתקנה</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. המדיניות מותקנת רק אחרי שכל החיבורים הפעילים ננתקים בכוח ומתחילים מחדש מול הכללים החדשים</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Install Policy הוא תהליך של שלושה שלבים: קומפילציה של המדיניות ב-Management, העברה לגייטווי, וטעינה ל-Kernel. הנקודה הקריטית שנבדקת לעיתים קרובות במבחן: חיבורים שכבר נבדקו ואושרו (Established Connections) ממשיכים להיות מותרים כי הם כבר רשומים בטבלת ה-State הקיימת של הגייטווי - הבדיקה מול ה-Rule Base מתבצעת רק לחיבורים חדשים. זו הסיבה שבדרך כלל התקנת מדיניות לא גורמת להפרעה משמעותית לתעבורה קיימת, בניגוד לתפיסה המוטעית שכל חיבור נבדק מחדש בכל Install Policy.</div>
</div>

<div class="quiz-card" data-answer="א">
  <p class="quiz-question"><strong>4. מה החיסרון המרכזי של AD Query מבחינת תזמון (Timing) בזיהוי משתמש, לעומת Identity Agent?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. AD Query מבוסס על קריאת אירועי Logon מתוך ה-Security Event Log של ה-Domain Controllers, ולכן קיים פער זמן קטן (delay) בין ההתחברות בפועל של המשתמש לתחנה לבין הרגע שהגייטווי מזהה אותו; Identity Agent מותקן ישירות בתחנת הקצה ומדווח את הזהות לגייטווי כמעט באופן מיידי</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. AD Query תמיד מהיר יותר מ-Identity Agent, בלי יוצא מן הכלל</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. שתי השיטות מזהות משתמש באותה מהירות בדיוק בכל תרחיש</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Identity Agent אינו תלוי כלל בסביבת Active Directory ולכן איטי יותר תמיד</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> AD Query הוא Agentless - הגייטווי (או ה-Management) קורא את אירועי ה-Logon מתוך ה-Security Event Logs של ה-Domain Controllers. מכיוון שזו שיטה מבוססת-קריאת-לוגים, קיים תמיד פער זמן קצר מסוים בין ההתחברות בפועל לזיהוי בגייטווי. Identity Agent, לעומת זאת, הוא תוכנה שרצה בתחנת הקצה עצמה ומדווחת ישירות לגייטווי ברגע ההתחברות - כך שהזיהוי מהיר ומדויק יותר, אך במחיר תקורת ניהול (Deployment) גבוהה יותר של הפצת Agent לכל תחנה.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>5. מהו ההבדל המרכזי בין VPN Community מסוג Star לבין Mesh, ומתי נכון לבחור ב-Star?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. ב-Mesh יש Center Gateway אחד וכל שאר הגייטווים הם Satellites שמתקשרים דרכו בלבד; ב-Star כולם מתקשרים ישירות זה עם זה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. ב-Star Community מגדירים Center Gateway/ים ו-Satellite Gateways, כאשר תעבורה זורמת בין Satellite ל-Center (ובאפשרות נוספת, גם Satellite-to-Satellite דרך ה-Center); ב-Mesh Community כל הגייטווים החברים בקהילה יכולים להקים מנהרת VPN ישירה זה עם זה ללא תלות ברכיב מרכזי - Mesh מתאים לארגון עם כמה סניפים שצריכים תקשורת ישירה מלאה ביניהם, בעוד Star מתאים לטופולוגיית Hub-and-Spoke (למשל סניפים שמתקשרים בעיקר מול מטה מרכזי)</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. שתי הטופולוגיות זהות לחלוטין מבחינה טכנית - ההבדל הוא רק בשם שנותנים ל-Community</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Mesh Community נתמכת רק ב-Remote Access VPN, ולא ב-Site-to-Site VPN בין גייטווים</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Star Community מתאימה לארגונים עם Hub-and-Spoke - יש Center Gateway מרכזי (למשל מטה) ו-Satellite Gateways (סניפים) שמדברים איתו; Mesh Community מתאימה כשכל האתרים צריכים לדבר ישירות אחד עם השני בלי "צוואר בקבוק" מרכזי. הבחירה הלא נכונה (למשל Mesh לארגון עם עשרות סניפים שרק צריכים לדבר עם המטה) יוצרת עומס מיותר של הקמת מנהרות רבות שלא בהכרח נחוצות.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>6. מבחינת אסטרטגיית אבטחה, למה Threat Extraction מוגדר כשיטה "מונעת" (Preventive) בעוד Threat Emulation מוגדר כ"מזהה" (Detective), למרות ששתיהן חלק מ-SandBlast?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. כי Threat Extraction תמיד איטי משמעותית יותר מ-Threat Emulation בכל תרחיש</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Threat Extraction מספק מיד למשתמש גרסה נקייה של הקובץ (מנוקה ממאקרואים ואובייקטים פעילים) בלי להמתין לתוצאת בדיקה - כך שהוא חוסם מראש כל תוכן זדוני פוטנציאלי בפורמט הבעייתי; Threat Emulation, לעומת זאת, מריץ את הקובץ המקורי בסביבת Sandbox ומחכה לתוצאה, ורק לאחר מכן מחליט אם לחסום או לשחרר אותו - כלומר קיים חלון זמן שבו התוצאה עדיין לא ידועה</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. כי Threat Emulation תמיד חוסם באופן גורף את כל הקבצים ללא יוצא מן הכלל</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. אין הבדל מהותי בין המנגנונים - שניהם "מונעים" באותה מידה בדיוק</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Threat Extraction (CDR) לא מנסה "לתפוס" תוכנה זדונית, אלא מנקה מראש כל אלמנט פעיל אפשרי (מאקרו, אובייקטים מוטמעים, קישורים) ומעביר גרסה נקייה מיידית - זו מניעה (Prevention) אמיתית שלא תלויה בזיהוי נכון. Threat Emulation מריץ את הקובץ בפועל ב-Sandbox ומחפש התנהגות זדונית - זהו זיהוי (Detection) שמבוסס על ניתוח, ולכן קיים תמיד חלון זמן קצר של המתנה לתוצאה, ותלות באיכות הזיהוי של המנוע.</div>
</div>

</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>8. מהו ההבדל המעשי בין <code>fw ctl zdebug drop</code> לבין <code>fw monitor</code> ככלי אבחון בגייטווי?</strong></p>
  <div class="quiz-options">

    <button class="quiz-option" type="button" data-choice="ג">ג. <code>fw monitor</code> מיועד אך ורק לניתוח לוגים היסטוריים ולא לתעבורה חיה בזמן אמת</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>fw ctl zdebug drop</code> דורש התקנת Agent נפרד על הגייטווי כדי לפעול</button>

<script>
(function () {
  function initQuiz() {
    var cards = document.querySelectorAll('.quiz-card');
    var scoreEl = document.getElementById('quiz-score');
    var resetAllBtn = document.getElementById('quiz-reset-all');

    function updateScore() {
      if (!scoreEl) return;
      var correctCount = document.querySelectorAll('.quiz-card--answered[data-was-correct="true"]').length;
      scoreEl.textContent = 'ענית נכון על ' + correctCount + ' מתוך ' + cards.length;
    }

    function answerCard(card, chosenBtn) {
      var correct = card.getAttribute('data-answer');
      var chosen = chosenBtn.getAttribute('data-choice');
      var isCorrect = chosen === correct;

      card.classList.add('quiz-card--answered');
      card.setAttribute('data-was-correct', isCorrect ? 'true' : 'false');

      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = true;
        if (opt.getAttribute('data-choice') === correct) {
          opt.classList.add('quiz-option--correct');
        } else if (opt === chosenBtn) {
          opt.classList.add('quiz-option--incorrect');
        }
      });

      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = isCorrect ? '✅ נכון!' : '❌ לא נכון - התשובה הנכונה מסומנת בירוק.';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
        result.classList.add(isCorrect ? 'quiz-result--correct' : 'quiz-result--incorrect');
      }

      updateScore();
    }

    function resetCard(card) {
      card.classList.remove('quiz-card--answered');
      card.removeAttribute('data-was-correct');
      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = false;
        opt.classList.remove('quiz-option--correct', 'quiz-option--incorrect');
      });
      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = '';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
      }
    }

    cards.forEach(function (card) {
      card.querySelectorAll('.quiz-option').forEach(function (btn) {
        btn.addEventListener('click', function () {
          if (card.classList.contains('quiz-card--answered')) return;
          answerCard(card, btn);
        });
      });
    });

    if (resetAllBtn) {
      resetAllBtn.addEventListener('click', function () {
        cards.forEach(resetCard);
        updateScore();
      });
    }

    updateScore();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initQuiz);
  } else {
    initQuiz();
  }
})();
</script>
