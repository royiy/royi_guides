## סקירת כלי הניטור

Check Point מספקת שכבת ניטור ולוגים עשירה, המורכבת ממספר רכיבים:

- **SmartConsole Logs & Monitor Tab** - הצפייה המרכזית בלוגים בזמן אמת ובהיסטוריה.
- **SmartLog** - מנוע חיפוש מהיר בלוגים (מבוסס אינדוקס, דומה ל-Search Engine).
- **SmartEvent** - שכבת קורלציה (Correlation) - מזהה תבניות מתקפה מתוך אלפי לוגים בודדים והופך אותם ל"אירועים" (Events) משמעותיים.
- **SmartView Monitor** (בגרסאות ישנות יותר) / **Monitoring Views** - ניטור ביצועים (CPU, Memory, Throughput, Connections) בזמן אמת.

## מבנה קובץ הלוג

כל שורת לוג ב-Check Point כוללת מידע עשיר: Source, Destination, Service, Action, Rule Number שהותאם, Blade שיצר את הלוג, Time, ולעיתים גם Application Name / User Identity אם רלוונטי.

## שימוש ב-SmartLog

SmartLog מאפשר חיפוש בשפה טבעית-יחסית, למשל:

```
src:192.168.1.10 AND action:Drop
blade:"IPS" AND severity:High
user:john.doe AND blade:"Application Control"
```

זהו כלי חובה לכל Troubleshooting יומיומי - הרבה יותר מהיר מסינון ידני של קבצי לוג גולמיים.

## SmartEvent - קורלציה ואנליטיקה

SmartEvent אוסף לוגים מכל הגייטווים ומזהה **תבניות** - למשל: 50 ניסיונות כניסה כושלים מאותו IP תוך 5 דקות = "Brute Force Attack Event". זה מאפשר ל-SOC (Security Operations Center) להתמקד באירועים חשובים במקום לטבוע באלפי לוגים בודדים.

תכונות מרכזיות:

- **Event Policy** - הגדרת חוקי קורלציה (Automatic Reactions ניתנות להגדרה - למשל שליחת מייל/הרצת סקריפט כשמתגלה אירוע).
- **Dashboards** - תצוגות גרפיות מותאמות אישית (Top Attackers, Top Blocked Applications וכו').
- **Reports** - דוחות מתוזמנים (יומי/שבועי) לניהול בכיר.

## פקודות CLI לניטור לוגים בגייטווי

```bash
# צפייה בלוג בזמן אמת מה-Gateway (raw)
fw log -f

# חיפוש בלוג לפי IP מקור
fw log -n | grep 192.168.1.10

# בדיקת סטטיסטיקת Blades בזמן אמת
cpstat fw
cpstat blades

# ניטור ביצועים חי (CPU, Memory, Connections)
top
netstat -i
fw ctl pstat
```

## `fw ctl pstat` - כלי מפתח לניטור ביצועים

זהו אחד הכלים החשובים ביותר לניטור בריאות הגייטווי - מציג מידע על **Kernel Memory**, **Connections Table Usage**, **Cookies**, **Fragments** ועוד:

```bash
fw ctl pstat
```

תפוקה גבוהה בטבלת ה-Connections (קרוב ל-Limit המוגדר) היא סימן אזהרה מוקדם לבעיות ביצועים או למתקפת DoS.

## דוגמה מעשית: חקירת אירוע חסימה

תרחיש: משתמש מתלונן שלא מצליח לגשת לאתר מסוים.

1. פותחים **Logs & Monitor** ב-SmartConsole, מסננים לפי Source IP של המשתמש והזמן המשוער.
2. מוצאים שורת Drop עם **Rule Number** מסוים.
3. עוברים ל-Rule Base, לוחצים על מספר הכלל שחסם - קופצים ישירות לכלל הרלוונטי.
4. בודקים אם החסימה מכוונת (Policy) או Application Control/URL Filtering חוסם קטגוריה.
5. במידת הצורך, מוסיפים חריגה (Exception) ממוקדת.

## הגדרת שליחת לוגים ל-SIEM חיצוני (Syslog)

ארגונים רבים משלבים את הלוגים של Check Point עם פתרון SIEM חיצוני (Splunk, QRadar וכו') דרך **Log Exporter**:

```bash
cp_log_export add name syslog_export target-server <SIEM_IP> target-port 514 protocol udp format syslog
cp_log_export restart
```

## טיפים וטריקים

- תמיד להתחיל חקירת תקלה מ-**SmartLog** ולא מ-CLI - הרבה יותר מהיר לסנן ולמצוא את השורה הרלוונטית.
- שימו לב ל-**Rule Number** בלוג - זו הדרך המהירה ביותר להבין "למה" חבילה נחסמה או אושרה.
- הגדירו **Retention Policy** נכונה - לוגים תופסים המון מקום, ויש למצוא איזון בין דרישות Compliance (שמירת לוגים X חודשים) לקיבולת אחסון.
- ב-SmartEvent, השקיעו זמן בכיוונון (Tuning) חוקי הקורלציה - חוקים "רועשים" מדי גורמים ל-Alert Fatigue אצל צוות ה-SOC.
- אם `fw ctl pstat` מראה שימוש גבוה ב-Connections Table - שקלו הגדלת ה-Table Size (בזהירות, תלוי ב-RAM) או חקרו למה יש כל כך הרבה חיבורים פתוחים.

## שאלות נפוצות לראיון עבודה בנושא זה

<details class="qa">
<summary>1. מה ההבדל בין SmartLog ל-SmartEvent?</summary>

SmartLog הוא מנוע חיפוש מהיר על הלוגים הגולמיים — שואלים "מה קרה לחבילה הזו" ומקבלים שורות. SmartEvent מבצע **קורלציה**: הוא מאחד אירועים לתבניות, מזהה מגמות ותקיפות, מציג dashboards ומפיק התרעות ודוחות. SmartLog לחקירה נקודתית, SmartEvent לתמונת מצב ולניהול אירועים.

</details>

<details class="qa">
<summary>2. איך הייתם מאתרים למה חבילה מסוימת נחסמה?</summary>

ב-SmartLog מסננים לפי Source, Destination, Service וטווח זמן, ובודקים בשורה את ה-Action, את ה-Blade שחסם ואת מספר/שם הכלל. אם ה-Blade הוא Firewall — עוברים לכלל עצמו ב-Rule Base; אם IPS/Anti-Bot — בודקים איזו הגנה פעלה. כשהלוג לא מספיק, יורדים ל-`fw monitor` כדי לראות אם החבילה בכלל הגיעה לגייטוויי ובאיזו נקודה נעלמה.

</details>

<details class="qa">
<summary>3. מה מציגה הפקודה <code>fw ctl pstat</code> ולמה היא חשובה לניטור?</summary>

היא מציגה סטטיסטיקות פנימיות של ה-Firewall kernel: זיכרון (hmem/kmem), מספר חיבורים בטבלת ה-Connections מול המגבלה, שימוש ב-NAT, ונתוני sync בקלאסטר. זו דרך מהירה לזהות מיצוי משאבים — למשל טבלת חיבורים שמתקרבת למקסימום — שמתבטא בתקלות "אקראיות" בתעבורה.

</details>

<details class="qa">
<summary>4. מה זה Log Exporter ולמה ארגונים משתמשים בו?</summary>

כלי מובנה שמייצא לוגים בזמן אמת לפורמטים סטנדרטיים (Syslog, CEF, LEEF) אל מערכות SIEM כמו Splunk או QRadar. ארגונים משתמשים בו כדי לרכז את כל מקורות הלוגים במקום אחד, לבצע קורלציה חוצת-מערכות ולעמוד בדרישות שימור ורגולציה.

</details>

<details class="qa">
<summary>5. מה זה Alert Fatigue ואיך מתמודדים איתו בהגדרת SmartEvent?</summary>

מצב שבו כמות ההתרעות כה גדולה עד שהצוות מפסיק להתייחס אליהן — וכך מתפספסת גם ההתרעה החשובה. מתמודדים באמצעות סינון וכוונון: להתריע רק על חומרה גבוהה, לאחד אירועים חוזרים לאירוע יחיד, להסיר False Positives ידועים, להגדיר ספי תדירות, ולנתב התרעות לפי סוג לצוות הנכון.

</details>

<details class="qa">
<summary>6. אילו שדות חשובים לבדוק בשורת לוג כדי לאבחן בעיה במהירות?</summary>

Time, Source ו-Destination, Service/Port, Action (Accept/Drop/Reject), ה-Blade שהפיק את הרשומה, מספר ושם הכלל, Interface וכיוון, ושדות ה-NAT (Xlate Source/Destination). לזיהוי — שם המשתמש, ולאיומים — שם ה-Protection ורמת החומרה.

</details>
