## גישה כללית לפתרון תקלות

לפני שרצים לפקודות, כדאי לעבוד לפי מתודולוגיה מסודרת:

1. **הגדירו את הבעיה במדויק** - איזו תעבורה, ממתי, אילו IP-ים, מה השגיאה בפועל?
2. **בדקו את השכבה הבסיסית** - חיבור פיזי/רשת (Layer 1-3) לפני שקופצים ל-Application Layer.
3. **בדקו לוגים** - SmartLog הוא תמיד תחנה ראשונה.
4. **שחזרו את הבעיה תוך ניטור חי** - `fw monitor`, `tcpdump` בזמן שהתקלה קורית.
5. **בודקים תצורה** - Rule Base, NAT, Routing, Objects.

## `fw monitor` - כלי הליבה לניתוח תעבורה

`fw monitor` מציג תעבורה במספר **נקודות אינספקציה (Inspection Points)** לאורך ה-Kernel Chain - מאפשר לראות בדיוק היכן חבילה "נעלמת" (למשל נכנסת אך לא יוצאת = נחסמה איפשהו בדרך).

```bash
# ניטור בסיסי לפי IP
fw monitor -e "accept host(192.168.1.10);" -o /tmp/capture.pcap

# ניטור עם כל 4 נקודות הבדיקה (i,I,o,O)
fw monitor -e "accept host(192.168.1.10) and port(80);"
```

נקודות המפתח: **i** (כניסה לפני Inspection), **I** (כניסה אחרי Inspection), **o** (יציאה לפני Inspection), **O** (יציאה אחרי Inspection). אם חבילה מופיעה ב-i אבל לא ב-I - היא נחסמה ע"י ה-Firewall.

## `tcpdump` - ניטור ברמת הרשת

```bash
tcpdump -i eth1 host 192.168.1.10 and port 443 -w /tmp/cap.pcap
```

בשונה מ-`fw monitor`, `tcpdump` בודק רק ברמת הממשק (לפני/אחרי הכל) - טוב לוודא שהתעבורה בכלל מגיעה לגייטווי.

## `fw ctl zdebug` - Debug מהיר ברמת הקרנל

```bash
fw ctl zdebug drop
```

מציג בזמן אמת למה חבילות נופלות (Dropped) - מצוין לזיהוי מהיר של חסימות לא צפויות (Anti-Spoofing, IP Options, וכו') שלא בהכרח מופיעות ב-Rule Base logs הרגילים.

## בעיות נפוצות ופתרונן

### 1. Anti-Spoofing Drop
תעבורה נחסמת עם הודעת "spoofed" - בד"כ בגלל Topology/Routing לא מוגדרים נכון על הממשק.

```bash
fw ctl zdebug drop | grep -i spoof
```
פתרון: לבדוק את הגדרת ה-Topology של הממשק הרלוונטי באובייקט הגייטווי (Manual Topology עם רשימת רשתות נכונה).

### 2. Policy Install נכשל
בד"כ בגלל שגיאת Syntax באובייקט, בעיית SIC, או קונפליקט בין כללים.

```bash
# בדיקת לוג ההתקנה האחרון
cat $FWDIR/log/fwm.elg | tail -100
```

### 3. ביצועים איטיים / CPU גבוה
```bash
top
fw ctl affinity -l -a   # בדיקת חלוקת CPU בין Interfaces ל-Firewall Instances
fw ctl multik stat      # בדיקת CoreXL - חלוקת עומס בין ליבות
```

### 4. בעיית SIC
```bash
cpconfig
# בדוק תוקף תעודה, אתחל SIC מחדש אם נדרש (Reset)
```

## CoreXL - הבנת חלוקת העומס בין ליבות

CoreXL הוא מנגנון שמאפשר לגייטווי לנצל מספר ליבות CPU במקביל לעיבוד תעבורה (Firewall Instances נפרדים). הבנתו קריטית לאבחון בעיות ביצועים:

```bash
fw ctl multik stat
```

מציג כמה Instances רצים ואיך העומס מחולק ביניהם - עומס לא מאוזן בין Instances הוא נורה אדומה.

## `cpinfo` - חבילת אבחון מקיפה

לפני פנייה לתמיכה (TAC) של Check Point, כמעט תמיד תתבקשו להריץ:

```bash
cpinfo -o /tmp/cpinfo_output.tgz
```

זה אוסף עשרות קבצי קונפיגורציה, לוגים וסטטיסטיקות במכה אחת - חוסך המון זמן.

## דוגמה מעשית: תקלת "משתמש לא מצליח לגלוש לאתר מסוים"

```
1. בדיקה ב-SmartLog: מחפשים src=<user_ip> dest=<site> - האם יש שורת Drop?
2. אם יש Drop -> בודקים באיזה Rule/Blade (Firewall? URL Filtering? Application Control?)
3. אם אין שום לוג -> ייתכן שהבעיה לא בגייטווי בכלל (DNS, Proxy אחר, בעיית לקוח)
4. הרצת fw monitor בזמן שהמשתמש מנסה לגלוש -> בדיקה אם החבילה בכלל מגיעה ל-i/I/o/O
5. אם ה-VPN/Routing מעורבים -> בדיקת vpn tu / routing table
```

## טיפים וטריקים

- **תמיד לתעד** את הפקודות וה-Debug שהרצתם ואת התוצאות - עוזר מאוד גם לכם וגם אם צריך להעביר את התקלה הלאה ל-TAC.
- `fw monitor` הוא הכלי החזק ביותר לזיהוי **היכן בדיוק** חבילה נעצרת בתוך ה-Kernel Chain - כדאי להשקיע זמן ללמוד אותו לעומק.
- זכרו לנקות Debug שהפעלתם (`fw ctl debug 0` / `vpn debug off`) - Debug Mode שנשאר פעיל יכול לפגוע בביצועים ולמלא דיסק בלוגים.
- שימוש בכלי **CPView** (`cpview` בטרמינל) נותן Dashboard טקסטואלי נוח לניטור ביצועים חי - Memory, CPU, Connections, Interfaces, הכל במקום אחד.

```bash
cpview
```
