מבחן אמריקאי קצר לבדיקה עצמית על כל מה שלמדתם לאורך מדריכי ה-Git (מבוא, ענפים ומיזוג, ביטול שינויים, Stash/Cherry-Pick, Remotes, Workflows, Internals, Hooks ואבטחה). בכל שאלה יש תשובה נכונה אחת. מפתח התשובות עם הסברים מופיע בסוף הדף.

---

## השאלות

**1. מה ההבדל העיקרי בין `git fetch` ל-`git pull`?**

א. אין הבדל, אלו שני שמות לאותה פקודה
ב. `fetch` מוריד עדכונים מה-remote בלי למזג אותם ל-branch הנוכחי, ו-`pull` מבצע `fetch` ואז `merge` (או `rebase`)
ג. `pull` מוריד רק metadata, ו-`fetch` מוריד גם את הקבצים
ד. `fetch` עובד רק על branch מרוחק, ו-`pull` עובד רק על branch מקומי

**2. פקודת ה-`git merge` מייצרת "Fast-Forward merge" מתי?**

א. תמיד, בכל מיזוג
ב. כשה-branch המטרה לא התקדם כלל מאז שה-branch שממזגים ממנו נוצר, כך שאפשר פשוט להזיז את המצביע קדימה
ג. כשיש קונפליקטים בין שני הענפים
ד. רק כשמשתמשים בדגל `--squash`

**3. מה עושה `git reset --hard HEAD~1`?**

א. מוחק את ה-commit האחרון מה-remote בלבד
ב. מזיז את ה-branch אחורה ב-commit אחד, ומאפס גם את ה-staging area וגם את ה-working directory למצב של אותו commit (השינויים הולכים לאיבוד)
ג. יוצר commit חדש שמבטל את השינויים של ה-commit האחרון, תוך שמירה על ההיסטוריה
ד. מעביר את ה-commit האחרון ל-stash

**4. מהו ההבדל המרכזי בין `git revert` ל-`git reset`?**

א. `revert` יוצר commit חדש שמבטל שינויים קודמים ושומר על ההיסטוריה, ואילו `reset` משנה/מוחק היסטוריה קיימת
ב. `revert` עובד רק על branch מרוחק, ו-`reset` רק על branch מקומי
ג. אין הבדל מעשי, שתי הפקודות שקולות
ד. `reset` בטוח יותר לשימוש על branch משותף מ-`revert`

**5. מתי משתמשים ב-`git stash`?**

א. כדי למחוק שינויים לצמיתות
ב. כדי לשמור זמנית שינויים לא-committed (staged ולא-staged) בצד, ולחזור אליהם מאוחר יותר - למשל כשצריך לעבור branch באמצע עבודה
ג. כדי ליצור branch חדש מה-commit הנוכחי
ד. כדי לדחוף (push) שינויים ל-remote בלי commit

**6. מה עושה `git cherry-pick <commit-hash>`?**

א. מוחק commit ספציפי מההיסטוריה של כל הענפים
ב. לוקח את השינויים מ-commit ספציפי מ-branch אחר ומחיל אותם כ-commit חדש על ה-branch הנוכחי
ג. יוצר tag חדש שמצביע על אותו commit
ד. ממזג שני branches לגמרי

**7. מהו ההבדל בין Merge ל-Rebase כאסטרטגיות שילוב היסטוריה?**

א. Merge יוצר commit מיזוג חדש ושומר על ההיסטוריה המקורית של שני הענפים; Rebase "משכתב" את ההיסטוריה ומניח מחדש את ה-commits שלך על גבי בסיס חדש, ויוצר היסטוריה ליניארית
ב. Rebase תמיד מהיר יותר אך אסור לשימוש בשום מצב
ג. Merge ו-Rebase מייצרים תמיד אותו hash של commit
ד. Rebase משמש רק למחיקת branches

**8. מה מייצג ה-hash של commit ב-Git (SHA-1/SHA-256)?**

א. מספר סידורי עולה שה-server מקצה לכל commit
ב. Checksum שמחושב מתוכן ה-commit (כולל snapshot של הקבצים, ה-parent, המחבר וההודעה) - כל שינוי קטן משנה את ה-hash לגמרי
ג. שם המשתמש שיצר את ה-commit, מוצפן
ד. מספר ה-branch שבו נוצר ה-commit

**9. מהו Git Hook, ולמה ישמש למשל `pre-commit`?**

א. פקודת Git להורדת קבצים מה-remote
ב. סקריפט שרץ אוטומטית בשלב מסוים במחזור החיים של Git (כמו לפני יצירת commit) - למשל להרצת linter או בדיקת סודות לפני שהקוד בכלל נכנס להיסטוריה
ג. כינוי (alias) מקוצר לפקודת `git commit`
ד. מנגנון להצפנת קבצים ב-repository

**10. אם דחפתם (push) בטעות סוד (API key) להיסטוריית Git ציבורית, מה הצעד הכי חשוב לבצע ראשון?**

א. למחוק את הקובץ מהקומיט האחרון עם `git rm` ולעשות push חדש
ב. להחליף (rotate) את הסוד מיידית אצל הספק - כי ברגע שנחשף יש להתייחס אליו כ"שרוף" גם אם ינוקה מההיסטוריה
ג. להפוך את ה-repository לפרטי ולסיים בכך
ד. להתעלם, כי Git שומר הכל בהצפנה ואף אחד לא יכול לגשת להיסטוריה ישנה

## מפתח תשובות והסברים

**1. תשובה נכונה: ב'**
`fetch` רק מסנכרן את המידע מה-remote (מעדכן branches מרוחקים כמו `origin/main`) בלי לגעת ב-branch המקומי שעליו אתם עובדים. `pull` הוא בעצם `fetch` + `merge`/`rebase` אוטומטי לתוך ה-branch הנוכחי.

**2. תשובה נכונה: ב'**
Fast-Forward קורה כשאין "התפצלות" אמיתית - ה-branch שאליו ממזגים לא זז מאז שהסתעפו ממנו, אז Git פשוט מזיז את המצביע (pointer) קדימה בלי ליצור commit מיזוג ייעודי.

**3. תשובה נכונה: ב'**
`--hard` הוא המסוכן מבין דגלי ה-reset - הוא לא רק מזיז את ה-branch, אלא גם דורס את ה-staging area וה-working directory. שינויים לא-committed הולכים לאיבוד לצמיתות (אלא אם נשמרו ב-stash לפני כן).

**4. תשובה נכונה: א'**
זו בדיוק הסיבה ש-`revert` בטוח לשימוש על branches משותפים/ציבוריים - הוא מוסיף commit חדש ולא מוחק/משנה כלום מההיסטוריה הקיימת. `reset` לעומת זאת יכול "למחוק" commits מההיסטוריה של ה-branch, מה שמסוכן אם כבר נדחפו ואחרים עובדים איתם.

**5. תשובה נכונה: ב'**
Stash הוא "מגירה" זמנית - שימושי כשצריך להחליף הקשר (למשל לעבור ל-branch אחר לתקן באג דחוף) בלי לעשות commit לעבודה חצי-מוגמרת.

**6. תשובה נכונה: ב'**
Cherry-pick מאפשר "לשאול" commit בודד מ-branch אחר בלי למזג את כל ה-branch - שימושי למשל כשצריך רק תיקון (hotfix) ספציפי אחד מ-branch פיתוח.

**7. תשובה נכונה: א'**
Merge שומר את ההיסטוריה המדויקת כפי שקרתה (כולל נקודות ההסתעפות), ואילו Rebase יוצר היסטוריה "נקייה" וליניארית - אבל משנה בפועל את ה-hashes של ה-commits, ולכן מסוכן לביצוע על branches ציבוריים ששותפים כבר משכו.

**8. תשובה נכונה: ב'**
ה-hash הוא לא מספר סידורי, אלא checksum קריפטוגרפי שמבוסס על התוכן עצמו - זו הסיבה ששני commits לעולם לא יקבלו את אותו hash אלא אם התוכן שלהם (כולל parent) זהה לחלוטין, וזו גם הבסיס לכך ש-Git יכול לזהות שינוי/שיבוש בהיסטוריה.

**9. תשובה נכונה: ב'**
Hooks הם סקריפטים מקומיים (לרוב ב-`.git/hooks/`, או מנוהלים דרך כלים כמו Husky) שמופעלים אוטומטית באירועים מסוימים. `pre-commit` למשל רץ לפני שה-commit נוצר בפועל, ומאפשר "לתפוס" בעיות (פורמט, סודות, בדיקות) לפני שהן בכלל נכנסות להיסטוריה.

**10. תשובה נכונה: ב'**
ניקוי היסטוריה (עם `filter-repo`/BFG) חשוב כניקיון נוסף, אבל לא מספיק כפתרון עצמאי - ברגע שסוד נחשף (במיוחד ב-repository ציבורי) יש להניח שהוא כבר נצפה/נשמר במקומות אחרים (caches, forks, סורקים אוטומטיים), ולכן רוטציה מיידית של הסוד היא הצעד הקריטי הראשון.
