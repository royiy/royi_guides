# מדריך 10: שאלות ראיון עבודה מקיפות + טיפים וטריקים כלליים ב-Jenkins

## מבוא
המדריך הזה הוא ריכוז מקיף של שאלות ראיון עבודה בכל הרמות (יסודי, בינוני, מתקדם), בתוספת טיפים וטריקים כלליים שלא כוסו לעומק במדריכים הקודמים. מומלץ לעבור גם על המדריכים 1-9 לפני ראיון.

## שאלות ברמה בסיסית

**ש: מה זה Jenkins ולמה משתמשים בו?**
ת: שרת אוטומציה open-source לבניית CI/CD pipelines - אוטומציה של build, test, ו-deploy של תוכנה. הוא מאפשר לזהות בעיות מוקדם (Continuous Integration) ולפרוס קוד בתדירות גבוהה ובאמינות (Continuous Delivery/Deployment).

**ש: מה ההבדל בין Continuous Integration, Continuous Delivery ו-Continuous Deployment?**
ת: CI - מיזוג קוד תדיר עם build/test אוטומטיים. Continuous Delivery - הקוד תמיד "ready to deploy" אך הפריסה עצמה דורשת אישור ידני. Continuous Deployment - כל שינוי שעובר את כל הבדיקות נפרס אוטומטית לפרודקשן ללא התערבות אנושית.

**ש: מה זה Freestyle Job לעומת Pipeline Job?**
ת: Freestyle הוא job מוגדר דרך UI טפסים (form-based), פשוט אך מוגבל וקשה ל-version control. Pipeline מוגדר כקוד (Jenkinsfile), נתמך ב-version control, תומך בלוגיקה מורכבת, ומהווה best practice מודרני.

**ש: איפה נשמרת ההיסטוריה של builds ב-Jenkins?**
ת: תחת `$JENKINS_HOME/jobs/<job-name>/builds/<build-number>/`, כולל לוגים, artifacts, ו-metadata.

**ש: מה זה Workspace ב-Jenkins?**
ת: תיקייה על ה-agent שבה ה-build בפועל רץ - שם נמצא הקוד שנמשך מ-Git ותוצרי ה-build הזמניים.

## שאלות ברמה בינונית

**ש: איך הייתם מתכננים pipeline ל-microservices עם 15 שירותים שונים?**
ת: כל שירות מקבל Jenkinsfile משלו (ב-repo שלו), עם Shared Library משותפת ל-לוגיקה חוזרת (build/test/deploy patterns). שימוש ב-Multibranch Pipeline או Organization Folder לגילוי אוטומטי. שקילת trigger בין שירותים תלויים (upstream/downstream jobs) בזהירות כדי לא ליצור race conditions.

**ש: מה ההבדל בין `archiveArtifacts` ל-`stash`?**
ת: `archiveArtifacts` שומר קבצים לצמיתות עם ה-build ב-Jenkins UI (נגיש גם אחרי סיום ה-pipeline). `stash` הוא זמני - שומר קבצים רק לתוך אותו pipeline run, כדי להעביר בין stages/agents שונים, ונמחק בסיום ה-run.

**ש: איך מטפלים ב-flaky tests בתוך pipeline?**
ת: שילוב `retry()` על stage הבדיקות, סימון tests לא יציבים ל-quarantine, מדידת flakiness rate לאורך זמן, ותיקון השורש (race conditions, תלות בסדר הרצה) במקום רק retry אינסופי.

**ש: מתי הייתם בוחרים ב-Scripted Pipeline על פני Declarative?**
ת: כשצריך לוגיקה דינמית מורכבת שקשה לבטא ב-Declarative (למשל יצירת stages דינמית בזמן ריצה בהתאם לתוכן קובץ), אבל ברוב המקרים Declarative עדיף ליכולות ה-validation וה-readability שלו, עם `script {}` blocks לחלקים מורכבים.

**ש: איך מודדים ומשפרים את זמן ריצת ה-pipeline?**
ת: שימוש ב-Timestamper plugin לזיהוי stages איטיים, parallel stages היכן שאפשר, caching (dependencies, Docker layers), agents חזקים יותר לעבודות כבדות, וצמצום unnecessary steps כמו checkout מלא כשלא נדרש.

**ש: מה זה Blue-Green Deployment ואיך אפשר לממש אותו ב-Jenkins Pipeline?**
ת: אסטרטגיית deployment ששומרת שני environments זהים (blue ו-green) - האחד live, השני עדכני. ב-Jenkins, ה-pipeline פורס לסביבה הלא-פעילה, מריץ smoke tests, ואז מחליף traffic (למשל דרך load balancer / Kubernetes service selector) - עם אפשרות rollback מיידי אם נכשל.

## שאלות ברמה מתקדמת

**ש: איך הייתם מתכננים Jenkins בסביבת enterprise עם מאות צוותים ואלפי jobs?**
ת: הפרדה לפי folders/teams עם RBAC (Role-based Authorization), Shared Libraries מרכזיות, Configuration as Code לתצורה שחוזרת על עצמה, Kubernetes cloud agents ל-scaling אלסטי, monitoring מרכזי (Prometheus plugin), וגיבויים אוטומטיים תקופתיים. שקילת controller נפרד לכל business unit אם ה-scale גדול מדי לcontroller יחיד.

**ש: מה ההבדל בין Vertical Scaling ל-Horizontal Scaling ב-Jenkins?**
ת: Vertical - הגדלת משאבי ה-controller/agent בודד (CPU/RAM). Horizontal - הוספת agents נוספים (סטטיים או דינמיים) כדי לפזר עומס builds. ברוב הארגונים המודרניים, Horizontal Scaling עם cloud agents (Kubernetes) עדיף כי הוא אלסטי ועמיד יותר.

**ש: איך Jenkins מטפל ב-pipeline resumability אחרי restart של ה-controller?**
ת: Declarative ו-Scripted Pipelines משתמשים ב-CPS (Continuation Passing Style) שמאפשר checkpoint של מצב ה-pipeline לדיסק. אחרי restart, Jenkins יכול להמשיך builds שהיו "durable" מהנקודה האחרונה שנשמרה, בתנאי שלא נעשה שימוש ב-`@NonCPS` בצורה שמפרה את זה.

**ש: מה ההבדל בין durability settings שונים ב-Pipeline (`PERFORMANCE_OPTIMIZED` מול `MAX_SURVIVABILITY`)?**
ת: `PERFORMANCE_OPTIMIZED` כותב checkpoints פחות תדיר לביצועים טובים יותר, אך מסתכן באובדן state רב יותר בקריסה. `MAX_SURVIVABILITY` כותב checkpoints לעיתים קרובות יותר - עמיד יותר לקריסות אך פוגע בביצועים. הבחירה תלויה ב-trade-off בין ביצועים ליציבות בסביבה הספציפית.

**ש: איך הייתם מבצעים migration של Jenkins מ-VM בודד ל-Kubernetes?**
ת: תכנון הדרגתי: קודם JCasC להעברת כל התצורה כקוד, בדיקת Shared Libraries שעובדות זהה, migration של agents ל-Kubernetes plugin עם pods אפמריים, בדיקת credentials migration, ולבסוף cut-over עם fallback plan אם יש בעיות.

**ש: מה ה-trade-offs בין Jenkins לכלי CI/CD מודרניים אחרים (GitHub Actions, GitLab CI, CircleCI)?**
ת: Jenkins מציע גמישות מקסימלית, self-hosting מלא, ועושר plugins עצום - אך דורש תחזוקה עצמאית (הרצה, שדרוגים, אבטחה). כלים כמו GitHub Actions/GitLab CI הם SaaS-first, עם הגדרה פשוטה יותר (YAML) ותחזוקה מינימלית מצד המשתמש, אך פחות גמישים לתרחישים מורכבים/on-premise ולפעמים יקרים יותר בסקייל גדול.

## תרחישי Troubleshooting (שאלות מבוססות תרחיש)

**ש: Build נכשל רק ב-Jenkins אבל עובד מקומית אצל המפתח - איך מתחילים לחקור?**
ת: בודקים הבדלי סביבה (JDK version, npm/node version, environment variables), בודקים אם ה-workspace נקי (`cleanWs()` לפני build), משווים dependencies שנטענים (lock files), ובודקים הרשאות filesystem על ה-agent.

**ש: Pipeline נתקע לנצח ב-stage מסוים בלי לוגים חדשים - מה בודקים?**
ת: בודקים אם יש `input` step שממתין לאישור ידני, בודקים deadlock אפשרי ב-`parallel` (למשל שני stages ממתינים זה לזה על משאב), בודקים אם ה-agent "תקוע" (thread dump דרך `/threadDump`), ומוסיפים `timeout()` למניעת מקרים דומים בעתיד.

**ש: כמות ה-jobs גדלה מאוד וה-Jenkins UI נהיה איטי מאוד - מה עושים?**
ת: מארגנים jobs ל-folders במקום רשימה שטוחה, מגבילים build history retention (`buildDiscarder`), עוברים ל-Configuration as Code לניהול יעיל יותר, ובודקים אם צריך יותר משאבים ל-controller (heap size) או פיצול ל-controllers נוספים.

**ש: איך מזהים ומטפלים ב-memory leak על ה-Jenkins controller?**
ת: ניטור heap usage (JVM metrics, Prometheus plugin), בדיקת plugins שידועים כבעייתיים (עדכון גרסאות), ניתוח heap dump (`jmap`), והגבלת מספר builds concurrent אם יש עומס יתר.

## טיפים וטריקים כלליים לעבודה יומיומית

- **Naming Convention עקבי**: שמרו על שמות jobs/stages ברורים ועקביים (`team-service-environment`) לניווט קל בסביבות גדולות.
- **Build Discarder תמיד מוגדר**: כדי לא להצטבר אלפי builds ישנים שתופסים דיסק:
  ```groovy
  options {
      buildDiscarder(logRotator(numToKeepStr: '30', artifactNumToKeepStr: '10'))
  }
  ```
- **Timestamps בלוגים**: התקינו Timestamper plugin - קריטי לדיבוג ביצועים.
- **Fail Fast**: אל תחכו עד סוף ה-pipeline לגלות כשל - הריצו lint/unit tests מוקדם ב-pipeline לפני integration tests יקרים.
- **Idempotent Deploys**: ודאו ש-deploy scripts אפשר להריץ שוב ושוב בלי תופעות לוואי לא רצויות.
- **Pipeline as Code בכל מקום**: אל תשאירו הגדרות חשובות רק ב-UI - הכל צריך להיות ב-Jenkinsfile/JCasC ותחת version control.
- **Notifications ממוקדות**: אל תשלחו הודעה על כל build - רק על שינויי status (success→failure, failure→success) כדי למנוע "alert fatigue".
- **תיעוד Runbooks**: לכל pipeline production-critical, תעדו מה לעשות אם הוא נכשל (rollback steps, escalation contacts).
- **בדקו Jenkinsfile לפני push**: השתמשו ב-VS Code extension או ב-linter endpoint לבדיקת syntax errors מראש.
- **גיבוי אוטומטי**: הגדירו job מתוזמן שמגבה את JENKINS_HOME (או לפחות config.xml, credentials.xml, jobs/) לאחסון חיצוני (S3, NFS).

## דוגמת Jenkinsfile "production-grade" מסכם (שילוב כל הטיפים)

```groovy
@Library('my-shared-lib') _

pipeline {
    agent { label 'docker' }

    options {
        timeout(time: 30, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '30'))
        disableConcurrentBuilds()
        timestamps()
    }

    environment {
        REGISTRY_CREDS = credentials('registry-creds')
    }

    stages {
        stage('Lint') {
            steps { sh 'npm run lint' }
        }
        stage('Test') {
            steps { sh 'npm test' }
            post { always { junit 'reports/*.xml' } }
        }
        stage('Build & Push') {
            when { branch 'main' }
            steps {
                sh 'docker build -t myorg/myapp:${GIT_COMMIT} .'
                sh 'docker push myorg/myapp:${GIT_COMMIT}'
            }
        }
        stage('Deploy to Staging') {
            when { branch 'main' }
            steps {
                deployToK8s(environment: 'staging', version: env.GIT_COMMIT)
            }
        }
        stage('Approval') {
            when { branch 'main' }
            steps {
                input message: 'לאשר deploy לפרודקשן?'
            }
        }
        stage('Deploy to Production') {
            when { branch 'main' }
            steps {
                deployToK8s(environment: 'production', version: env.GIT_COMMIT)
            }
        }
    }

    post {
        success { notifySlack('SUCCESS') }
        failure { notifySlack('FAILURE') }
        always { cleanWs() }
    }
}
```
