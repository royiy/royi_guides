<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>1. מהו ה-runtime הרשמי של קונטיינרים ב-OpenShift על צמתי ה-Worker, ומה תפקיד ה-openshift-apiserver ב-Control Plane?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Docker Engine הוא ה-runtime, ו-openshift-apiserver מחליף לחלוטין את kube-apiserver</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. CRI-O הוא ה-runtime הרשמי (לא Docker), ו-openshift-apiserver מוסיף שכבת API נוספת למשאבים הייחודיים ל-OpenShift (Routes, Builds, ImageStreams)</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. containerd הוא ה-runtime, ו-openshift-apiserver משמש רק לניהול RHCOS</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. אין runtime ייעודי - OpenShift משתמש ב-runtime שהאדמין בוחר, ו-openshift-apiserver הוא רק דשבורד גרפי</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> CRI-O הוא ה-container runtime הרשמי של OpenShift על צמתי ה-Worker (לא Docker). ה-openshift-apiserver רץ לצד kube-apiserver ומוסיף שכבת API עבור המשאבים הייחודיים ל-OpenShift כמו Route, BuildConfig ו-ImageStream, שאינם קיימים ב-Kubernetes וניל.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>2. למה מומלץ להעדיף את פקודת <code>oc</code> על פני <code>kubectl</code> בעבודה מול קלאסטר OpenShift?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. כי kubectl כלל לא עובד מול קלאסטר OpenShift</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. כי oc מהיר יותר בביצועים בגלל מימוש שונה של פרוטוקול ה-API</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. כי oc מודע למשאבים הייחודיים ל-OpenShift (Route, BuildConfig, Project, DeploymentConfig) ומספק פקודות עזר נוספות כמו <code>oc new-app</code>, <code>oc rsh</code> ו-<code>oc debug</code></button>
    <button class="quiz-option" type="button" data-choice="ד">ד. כי kubectl דורש רישיון בתשלום נפרד מ-Red Hat</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> kubectl עובד מצוין מול קלאסטר OpenShift לכל מה שמשותף ל-Kubernetes, אבל אינו מודע למשאבים הייחודיים ל-OpenShift (Route, BuildConfig, Project, DeploymentConfig) ולא מגיע עם פקודות עזר כמו <code>oc new-app</code>, <code>oc rsh</code> או <code>oc debug</code>, ולכן oc הוא הבחירה המומלצת.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>3. מה ההבדל המרכזי בין Deployment ל-DeploymentConfig, ומה ההמלצה הרשמית של Red Hat כיום?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין הבדל מעשי, זה רק שם ישן וחדש לאותו אובייקט</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Deployment הוא native ל-Kubernetes ומנוהל ע"י ReplicaSet, ואילו DeploymentConfig ייחודי ל-OpenShift ומנוהל ע"י ReplicationController; Red Hat ממליצה כיום להשתמש ב-Deployment הרגיל בפרויקטים חדשים</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. DeploymentConfig מהיר יותר כי הוא לא תומך ב-Rolling Update בכלל</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Deployment תומך רק בקונטיינר אחד לכל פוד, ו-DeploymentConfig תומך במספר קונטיינרים</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> DeploymentConfig הוא ה-resource ה"היסטורי" הייחודי ל-OpenShift, ותומך ב-triggers אוטומטיים מ-ImageStream ו-lifecycle hooks שאין ב-Deployment, אך הוא deprecated - Red Hat ממליצה משנת 2019 להשתמש ב-Deployment הרגיל (native ל-Kubernetes) בכל פרויקט חדש.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>4. מהו Route ב-OpenShift, ובמה הוא שונה מ-Service?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Route הוא זהה ל-Service, רק בשם אחר להתאמה למינוח של Red Hat</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Service מספק כתובת יציבה בתוך הקלאסטר בלבד, ואילו Route (המנוהל ע"י HAProxy Router) חושף שירות פנימי קיים לרשת החיצונית, ותמיד "יושב" מעל Service - לא ניתן לחשוף פוד ישירות דרכו</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. Route מיועד רק לתעבורת TCP גולמית, ו-Service מיועד רק ל-HTTP</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Route קיים גם ב-Kubernetes וניל, בעוד Service קיים רק ב-OpenShift</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Route הוא ה-resource הייחודי ל-OpenShift לחשיפת שירות פנימי החוצה, מנוהל ע"י HAProxy Router, ותמיד מפנה ל-Service קיים (אם ה-Service שגוי, ה-Route "יעבוד" אבל יחזיר 503). Service, לעומת זאת, מספק כתובת יציבה נגישה רק בתוך הקלאסטר.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>5. מה עושה S2I (Source-to-Image), ומה היתרון של ImageStream בשילוב איתו?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. S2I כותב Dockerfile אוטומטית ושומר אותו ב-Git; ImageStream רק מציג היסטוריית commits</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. S2I מריץ בדיקות אבטחה (scanning) על תמונות קיימות; ImageStream שומר את תוצאות הסקירה</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. S2I בונה תמונת container מקוד מקור ב-Git ו-builder image, בלי Dockerfile ידני; ImageStream עוקב אחר תגיות התמונה ומאפשר trigger אוטומטי לעדכון Deployment/DC כשמגיעה תמונה חדשה - בלי צורך ב-webhook חיצוני</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. S2I ו-ImageStream שניהם מיועדים רק לניהול Secrets של registry פרטי</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> S2I לוקח קוד מקור מ-Git ו-builder image (כמו Node.js/Python) ומייצר תמונת container מוכנה, בלי לכתוב Dockerfile. ImageStream הוא ה"Git for Images" של OpenShift - הוא עוקב אחר תגיות תמונה, וכל משאב שמצביע על ImageStreamTag (כמו DeploymentConfig) יכול לקבל trigger אוטומטי כשמגיעה תמונה חדשה.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>6. מה ההבדל בין accessMode <code>ReadWriteOnce</code> (RWO) ל-<code>ReadWriteMany</code> (RWX) עבור PVC, ולמה זה חשוב?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. RWO מאפשר קריאה בלבד, RWX מאפשר גם כתיבה - אין קשר למספר ה-nodes</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. RWO מאפשר ל-node אחד בלבד לכתוב לאותו volume, RWX מאפשר למספר nodes לכתוב בו-זמנית; לא כל StorageClass תומך ב-RWX (AWS EBS/GCP PD רגילים לא תומכים, NFS/Ceph/Azure Files כן)</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. RWO מיועד רק ל-ConfigMaps, RWX מיועד רק ל-Secrets</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. אין הבדל אמיתי, זו רק תיעוד לצורך קריאות בלבד</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> RWO מתאים לרוב מסדי הנתונים כי node אחד בלבד יכול לכתוב אליו (מונע כתיבה כפולה לא מתואמת). RWX נדרש כשיש צורך בשיתוף קבצים בין מספר nodes/פודים במקביל, אבל תלוי לחלוטין ב-backend של האחסון - ניסיון ליצור PVC עם RWX על StorageClass שלא תומך בכך יגרום ל-Pending לנצח.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>7. מדוע יצירת Pod עם <code>securityContext.runAsUser: 0</code> נכשלת בדרך כלל ב-OpenShift, ומה הפתרון הנכון?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. זה מעולם לא נכשל ב-OpenShift, זה מוגבל רק ב-Kubernetes וניל</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. ה-SCC (Security Context Constraints) ברירת המחדל <code>restricted-v2</code> אוסר ריצה כ-root (UID 0) ומחייב UID רנדומלי; הפתרון הנכון הוא לתקן את ה-Dockerfile כדי לרוץ עם USER לא-root, ולא להעניק <code>anyuid</code> שנחשב security anti-pattern</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. יש לפתוח קריאת תמיכה ל-Red Hat כדי לבטל את המגבלה עבור כל הקלאסטר</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. יש להוסיף את הפוד ל-namespace בשם <code>openshift-operators</code> שבו אין הגבלות SCC</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> זו שגיאת ה-SCC הכי נפוצה למי שמגיע מ-Docker רגיל. SCC הוא מנגנון אבטחה ייחודי ל-OpenShift (אין ב-Kubernetes וניל) שאין ב-restricted-v2 מאפשר UID 0. הפתרון הנכון הוא לתקן את ה-Dockerfile (<code>USER 1001</code> וכו') ולא להעניק <code>anyuid</code>, שפותח פרצת אבטחה.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>8. מה ההבדל בין Helm ל-Operator, ומתי כדאי להעדיף אחד על השני?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Helm ו-Operator זהים לגמרי, ההבדל היחיד הוא שם החברה שמפתחת אותם</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Operator הוא תמיד חלק מ-Helm, אי אפשר להשתמש באחד בלי השני</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. Helm מתמקד בפריסה חד-פעמית (templating + install) בלי לוגיקה תפעולית מתמשכת; Operator מריץ Reconciliation Loop מתמיד ומתאים לאפליקציות stateful מורכבות (DB, message queues) שדורשות ניהול אוטומטי מתמשך כמו backup ותיקון תקלות</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Helm מיועד רק ל-OpenShift, Operator מיועד רק ל-Kubernetes וניל</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Helm מתאים לפריסות "set and forget" ללא לוגיקה תפעולית מתקדמת. Operator (המבוסס על CRD ומנוהל דרך OLM) מריץ Reconciliation Loop מתמיד ומתאים לאפליקציות מורכבות שדורשות תיקון תקלות, שדרוגים וגיבויים אוטומטיים - כמו מסדי נתונים מבוזרים.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>9. מהו התפריט המובנה ל-monitoring ב-OpenShift, ומה תפקיד ה-Cluster Monitoring Operator?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. OpenShift לא מגיע עם monitoring מובנה בכלל - חייבים להתקין Datadog או New Relic בנפרד</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Cluster Monitoring Operator מפעיל כברירת מחדל ערימת Prometheus (מטריקות), Alertmanager (התראות) ו-Thanos (retention מורחב), עם דשבורדים בקונסולה; אפשר גם להפעיל User Workload Monitoring כדי לנטר אפליקציות משתמש דרך ServiceMonitor</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. הוא רק ה-UI הגרפי, ואינו אוסף שום מטריקה בעצמו</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. הוא מנטר רק את מצב ה-etcd ואינו נותן מידע על אפליקציות</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> OpenShift מגיע עם ערימת monitoring מובנית ופעילה כברירת מחדל, מבוססת Prometheus, Alertmanager ו-Thanos. הפעלת <code>enableUserWorkload: true</code> מוסיפה Prometheus נוסף שסורק ServiceMonitor/PodMonitor שמשתמשים יוצרים בפרויקטים שלהם, כדי לנטר גם את האפליקציות עצמן ולא רק את הקלאסטר.</div>
</div>

<div class="quiz-card" data-answer="א">
  <p class="quiz-question"><strong>10. פוד עולה ואז נכנס למצב <code>CrashLoopBackOff</code>. מה שני הצעדים הראשונים בזרימת האבחון המומלצת, ומה ההבדל בין readinessProbe ל-livenessProbe שכדאי לזכור באבחון כזה?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. <code>oc describe pod</code> לבדוק events ולוגים ב-<code>oc logs --previous</code>; readinessProbe קובע אם הפוד מקבל תעבורה (כשל=הסרה מה-Service בלי הרג), ואילו livenessProbe קובע אם צריך restart - בלבול בין השניים גורם ל-restart loops מיותרים</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. למחוק את הפוד מיידית וליצור מחדש; readinessProbe ו-livenessProbe הם שם אחר לאותו מנגנון</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. להגדיל ישירות את מספר ה-replicas; readinessProbe רץ רק פעם אחת בעלייה, livenessProbe רץ כל הזמן</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. להריץ <code>oc adm must-gather</code> תמיד לפני כל בדיקה אחרת; אין הבדל מעשי בין שתי ה-probes</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> זרימת האבחון השיטתית מתחילה ב-<code>oc describe pod</code> (מקטע Events בתחתית) ו-<code>oc logs --previous</code> לראות את הלוגים מהריצה שקרסה. חשוב גם להבחין בין readinessProbe (מסיר מה-Service בלי לפגוע בפוד עצמו) ל-livenessProbe (מפעיל restart) - בלבול בין השתיים גורם ל-restart loops מיותרים כשהבעיה בעצם זמנית, כמו חיבור איטי ל-DB.</div>
</div>

<script>
(function () {
  function initQuiz() {
    var cards = document.querySelectorAll('.quiz-card');
    var scoreEl = document.getElementById('quiz-score');
    var resetAllBtn = document.getElementById('quiz-reset-all');

    function updateScore() {
      if (!scoreEl) return;
      var correctCount = document.querySelectorAll('.quiz-card--answered[data-was-correct="true"]').length;
      scoreEl.textContent = 'ענית נכון על ' + correctCount + ' מתוך ' + cards.length;
    }

    function answerCard(card, chosenBtn) {
      var correct = card.getAttribute('data-answer');
      var chosen = chosenBtn.getAttribute('data-choice');
      var isCorrect = chosen === correct;

      card.classList.add('quiz-card--answered');
      card.setAttribute('data-was-correct', isCorrect ? 'true' : 'false');

      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = true;
        if (opt.getAttribute('data-choice') === correct) {
          opt.classList.add('quiz-option--correct');
        } else if (opt === chosenBtn) {
          opt.classList.add('quiz-option--incorrect');
        }
      });

      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = isCorrect ? '✅ נכון!' : '❌ לא נכון - התשובה הנכונה מסומנת בירוק.';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
        result.classList.add(isCorrect ? 'quiz-result--correct' : 'quiz-result--incorrect');
      }

      updateScore();
    }

    function resetCard(card) {
      card.classList.remove('quiz-card--answered');
      card.removeAttribute('data-was-correct');
      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = false;
        opt.classList.remove('quiz-option--correct', 'quiz-option--incorrect');
      });
      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = '';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
      }
    }

    cards.forEach(function (card) {
      card.querySelectorAll('.quiz-option').forEach(function (btn) {
        btn.addEventListener('click', function () {
          if (card.classList.contains('quiz-card--answered')) return;
          answerCard(card, btn);
        });
      });
    });

    if (resetAllBtn) {
      resetAllBtn.addEventListener('click', function () {
        cards.forEach(resetCard);
        updateScore();
      });
    }

    updateScore();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initQuiz);
  } else {
    initQuiz();
  }
})();
</script>
