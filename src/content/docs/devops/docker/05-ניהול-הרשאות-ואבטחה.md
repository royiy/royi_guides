# ניהול הרשאות ואבטחה ב-Docker

## למה זה חשוב?

בברירת מחדל, תהליכים בתוך קונטיינר Docker רצים כ-**root** (UID 0), ובגלל שהקונטיינר חולק Kernel עם המארח, פרצת אבטחה בקונטיינר עלולה להוביל ל"בריחה" (container escape) ולפגיעה במארח עצמו. לכן ניהול הרשאות הוא נושא קריטי.

## הרצת קונטיינר כמשתמש לא-root

### דרך 1: בזמן ריצה

```bash
docker run -u 1000:1000 myapp
docker run --user myuser myapp
```

### דרך 2: ב-Dockerfile (הדרך המומלצת)

```dockerfile
FROM node:20-alpine

# יצירת משתמש וקבוצה ייעודיים
RUN addgroup -g 1001 appgroup && \
    adduser -D -u 1001 -G appgroup appuser

WORKDIR /app
COPY --chown=appuser:appgroup . .

# מעבר למשתמש הלא-פריווילגי
USER appuser

CMD ["node", "server.js"]
```

many images רשמיים (כמו node) כבר כוללים משתמש `node` מובנה - אפשר פשוט:
```dockerfile
USER node
```

## Capabilities - שליטה עדינה בהרשאות

במקום "הכל או כלום" (root או לא), לינוקס מחלק הרשאות root ל-**capabilities** נפרדות. Docker מגביל כברירת מחדל סט מסוים של capabilities, אבל אפשר לכוונן:

```bash
# הסרת כל ה-capabilities והוספה סלקטיבית
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE myapp

# הסרת capability ספציפית
docker run --cap-drop=NET_RAW myapp
```

Capabilities נפוצות:
- `NET_BIND_SERVICE` - קישור לפורטים מתחת ל-1024
- `SYS_ADMIN` - הרשאות מנהל מערכת רחבות (מסוכן, כמעט אף פעם לא נחוץ)
- `NET_RAW` - יצירת raw sockets (שימושי ל-ping, מסוכן פוטנציאלית)

**כלל אצבע לפרודקשן:** `--cap-drop=ALL` ואז הוספה מפורשת רק של מה שבאמת נדרש.

## Read-only Filesystem

מניעת שינוי במערכת הקבצים של הקונטיינר - מקטין משמעותית את משטח התקיפה:

```bash
docker run --read-only myapp

# אם האפליקציה צריכה לכתוב לתיקייה זמנית ספציפית:
docker run --read-only --tmpfs /tmp myapp
```

## הרצה ללא הרשאות נוספות (no-new-privileges)

מונע מהתהליך בתוך הקונטיינר לקבל הרשאות נוספות מעבר למה שכבר יש לו (חוסם למשל ניצול בינארי עם bit setuid):

```bash
docker run --security-opt=no-new-privileges myapp
```

## הרשאות על ה-Docker Socket

חשיפת `/var/run/docker.sock` לקונטיינר (נפוץ בכלי CI/CD) שקולה בפועל למתן הרשאות **root מלאות על המארח**:

```bash
# ⚠️ מסוכן מאוד - נותן שליטה מלאה על ה-Docker daemon (ולכן על המארח)
docker run -v /var/run/docker.sock:/var/run/docker.sock myapp
```

אם חובה לעשות זאת (למשל, כלי CI שצריך להריץ קונטיינרים), שקלו:
- שימוש ב-Docker socket proxy עם הרשאות מוגבלות (למשל [docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy))
- הרצה ב-rootless mode
- שימוש בפתרונות ייעודיים כמו Sysbox או Kata Containers לבידוד חזק יותר

## Rootless Docker (ה-daemon עצמו רץ ללא root)

מעבר להרצת קונטיינרים כלא-root, אפשר להריץ את **כל ה-Docker daemon** ללא הרשאות root:

```bash
# התקנת rootless mode
curl -fsSL https://get.docker.com/rootless | sh

# הוספת המשתנים הנדרשים
export PATH=/home/$USER/bin:$PATH
export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock
```

זה מוסיף שכבת הגנה נוספת - גם אם קונטיינר "בורח", הוא עדיין מוגבל להרשאות המשתמש הרגיל ולא root.

## User Namespace Remapping

מאפשר ל-root **בתוך** הקונטיינר להיות ממופה ל-UID לא-פריווילגי **במארח**:

ב-`/etc/docker/daemon.json`:
```json
{
  "userns-remap": "default"
}
```

כך גם אם תהליך בתוך הקונטיינר "חושב" שהוא root (UID 0), במארח עצמו הוא ממופה למשתמש רגיל ללא הרשאות.

## הגבלת משאבים (מניעת DoS)

```bash
docker run \
  --memory="512m" \
  --memory-swap="512m" \
  --cpus="1.0" \
  --pids-limit=100 \
  myapp
```

`--pids-limit` חשוב במיוחד למניעת fork bombs שיכולים להפיל את כל המארח.

## סריקת Images לחולשות אבטחה

```bash
# Docker Scout (מובנה)
docker scout cves myimage:latest

# כלי חיצוני נפוץ - Trivy
trivy image myimage:latest
```

## Secrets - איך *לא* לעשות ואיך כן

```dockerfile
# ❌ אסור! הסוד נשאר בהיסטוריית ה-image לצמיתות
ENV DB_PASSWORD=supersecret123
RUN echo "DB_PASSWORD=supersecret123" >> .env
```

**הדרך הנכונה** - Docker Secrets (ב-Swarm) או mount זמני בזמן build:

```dockerfile
# BuildKit secret mount - לא נשמר ב-layer!
RUN --mount=type=secret,id=db_password \
    DB_PASS=$(cat /run/secrets/db_password) && \
    echo "using password securely"
```

```bash
docker build --secret id=db_password,src=./password.txt -t myapp .
```

בזמן ריצה - השתמשו במשתני סביבה שמוזרקים מבחוץ (לא ב-Dockerfile), או בפתרונות ייעודיים כמו HashiCorp Vault, AWS Secrets Manager, או Docker Swarm Secrets/Kubernetes Secrets.

## סיכום Checklist לאבטחה בפרודקשן

- [ ] `USER` לא-root ב-Dockerfile
- [ ] `--cap-drop=ALL` + הוספה סלקטיבית של capabilities נדרשות
- [ ] `--read-only` filesystem כשאפשר
- [ ] `--security-opt=no-new-privileges`
- [ ] הגבלת משאבים (`--memory`, `--cpus`, `--pids-limit`)
- [ ] סריקת images באופן קבוע (Trivy/Docker Scout)
- [ ] אל תחשפו את `docker.sock` אלא אם הכרחי
- [ ] Images מגרסה קבועה, לא `latest`
- [ ] Multi-stage builds להקטנת משטח התקיפה
- [ ] סודות לא ב-Dockerfile ולא ב-ENV קבועים

## טיפים וטריקים

- בדקו את משתמש ברירת המחדל של image לפני שימוש: `docker run --rm image whoami`
- `docker scan` הוחלף ב-`docker scout` בגרסאות חדשות של Docker Desktop.
- אם image רשמי לא כולל משתמש לא-root, לרוב אפשר למצוא בדוקומנטציה שלו הנחיה איך ליצור אחד.
- `--cap-drop=ALL --cap-add=X` תמיד עדיף על השארת ברירת המחדל - עקרון ההרשאה המינימלית (Principle of Least Privilege).

## שאלות ראיון נפוצות בנושא

1. **למה מסוכן להריץ קונטיינר כ-root?**
   כי אם יש חולשת אבטחה שמאפשרת "בריחה" מהקונטיינר (container escape), התוקף יקבל הרשאות root ישירות על המארח, לא רק בתוך הקונטיינר המבודד.

2. **מה ההבדל בין הרצת קונטיינר עם `--user 1000` לבין `userns-remap`?**
   `--user` קובע איזה UID רץ *בתוך* הקונטיינר; `userns-remap` ממפה UIDs בתוך הקונטיינר (כולל root=0) ל-UIDs לא-פריווילגיים *במארח* - שכבת הגנה נוספת ועמוקה יותר.

3. **למה חשיפת `docker.sock` לקונטיינר מסוכנת?**
   כי זה נותן לקונטיינר שליטה מלאה על ה-Docker daemon, שיכול ליצור קונטיינרים חדשים עם הרשאות מלאות על המארח - בפועל שקול ל-root access על השרת.

4. **מה זה Linux Capabilities ולמה עדיף להשתמש בהם על פני "all or nothing"?**
   Capabilities מחלקים את הרשאות root לחלקים נפרדים (למשל יכולת לקשור פורט נמוך, יכולת ליצור raw socket). זה מאפשר לתת רק את ההרשאה המינימלית הנדרשת במקום root מלא.

5. **איך מוודאים שסוד (כמו סיסמת דאטהבייס) לא "נדלף" בתוך image?**
   לא לשים אותו ב-`ENV`/`ARG`/`RUN echo` קבועים ב-Dockerfile; להשתמש ב-BuildKit secret mounts בזמן build, ובמשתני סביבה שמוזרקים חיצונית (לא נכתבים ל-image) בזמן ריצה.
