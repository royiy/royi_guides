מבחן אינטראקטיבי ברמת קושי גבוהה, בסגנון שאלות הסמכת **Docker Certified Associate (DCA)** - בניגוד למבחן החזרה הכללי בפרק הקודם, כאן כל שאלה בודקת נקודה עדינה ומטעה שדורשת הבנה אמיתית של מנגנוני הפנים של Docker (Image Layers, Networking, Swarm, אבטחה ועוד), לא רק שינון. בחרו תשובה ותקבלו מיד משוב עם הסבר מפורט.

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>2. מהו ההבדל המרכזי בין רשת <code>overlay</code> לרשת <code>bridge</code> ב-Docker, ומתי חובה להשתמש ב-<code>overlay</code>?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. <code>overlay</code> מוגבלת לתקשורת בתוך host בודד בלבד, בעוד <code>bridge</code> תומכת בתקשורת בין hosts שונים</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. <code>overlay</code> מאפשרת תקשורת בין קונטיינרים הרצים על nodes (hosts) שונים כחלק מ-cluster, בעוד <code>bridge</code> (ברירת המחדל) מוגבלת לתקשורת בין קונטיינרים על אותו host בלבד - חובה להשתמש ב-<code>overlay</code> כשעובדים עם Swarm services הפרוסים על כמה nodes</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. אין הבדל מעשי בין השתיים - שתיהן זהות לחלוטין בהתנהגותן</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>overlay</code> משמשת אך ורק לחיבור קונטיינר יחיד לאינטרנט החיצוני</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> רשת <code>bridge</code> (ברירת המחדל) מוגבלת לקונטיינרים הרצים על אותה מכונה. רשת <code>overlay</code> "פורשת" רשת וירטואלית מעל כמה Docker daemons (nodes) בעזרת VXLAN, ומאפשרת לקונטיינרים על nodes שונים ב-Swarm cluster לתקשר ביניהם כאילו הם על אותה רשת. לשם השוואה: <code>host</code> מבטלת בידוד רשת ומשתמשת ישירות בסטאק הרשת של המארח, ו-<code>macvlan</code> מקצה לקונטיינר כתובת MAC משלו כך שהוא נראה כמכשיר פיזי נפרד ברשת הפיזית.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>3. מה ההבדל המרכזי בין Named Volume ל-Bind Mount, ומתי מומלץ להעדיף Named Volume?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Bind Mount מנוהל לחלוטין ע"י Docker בתוך <code>/var/lib/docker/volumes</code>, ואילו Named Volume מצביע לנתיב שרירותי כלשהו במערכת הקבצים של המארח</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Named Volume מנוהל ע"י Docker (נשמר תחת <code>/var/lib/docker/volumes</code>, ניתן לגיבוי ולניהול בקלות דרך <code>docker volume</code>), בעוד Bind Mount מצביע לנתיב ספציפי וקיים מראש על המארח - Named Volume מומלץ לפרודקשן ולנתונים שהאפליקציה מנהלת (כמו דאטהבייס), ו-Bind Mount שימושי בעיקר לפיתוח (למשל הזרקת קוד מקור חי לתוך הקונטיינר)</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. אין הבדל טכני בין השניים, ההבדל הוא רק בתחביר הפקודה</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. רק Bind Mount שורד מחיקת קונטיינר; Named Volume נמחק תמיד יחד עם הקונטיינר שהשתמש בו</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Named Volume הוא אובייקט שמנוהל לגמרי ע"י Docker - נוצר ונמחק דרך <code>docker volume create/rm</code>, ואינו תלוי במבנה תיקיות ספציפי במארח, מה שהופך אותו לניתן להעברה בין hosts ולגיבוי בצורה סטנדרטית. Bind Mount לעומת זאת ממפה נתיב מוחלט וקיים במארח (למשל <code>./src:/app/src</code>), נוח לפיתוח כי שינוי קוד מקומי משתקף מיד בקונטיינר, אך פחות מבודד ותלוי במבנה הקבצים של המארח הספציפי.</div>
</div>

    <button class="quiz-option" type="button" data-choice="ב">ב. 3</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. 2</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. 1</button>

  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Swarm משתמש באלגוריתם Raft consensus, שדורש רוב (majority) פעיל של managers כדי לקבל החלטות. עם 5 managers, נדרש רוב של 3 כדי לשמור על quorum, ולכן ניתן לאבד עד 2 managers (<code>(n-1)/2 = (5-1)/2 = 2</code>) בלי לאבד את היכולת לנהל את ה-cluster. אם ייפלו 3 או יותר, ה-cluster ייכנס למצב read-only ולא יוכלו לבצע שינויים חדשים עד שחלק מה-managers יחזרו לפעול.</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>5. מדוע קונטיינרים נחשבים לרוב לבידוד "חלש יותר" מבחינה אבטחתית בהשוואה למכונות וירטואליות (VMs), על אף השימוש ב-Namespaces וב-Cgroups?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. כי קונטיינרים תמיד רצים כ-root וללא שום אפשרות לשנות זאת</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. כי כל הקונטיינרים על אותו host משתפים את אותו kernel של מערכת ההפעלה המארחת - בעוד כל VM מריצה kernel נפרד משלה מעל Hypervisor; פגיעות ב-kernel המשותף עלולה לאפשר "בריחה" (container escape) שחושפת את המארח ואת שאר הקונטיינרים, סיכון שלא קיים באותה צורה מול VM עם קרנל מבודד לחלוטין</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. כי Namespaces ו-Cgroups הם פיצ'רים קוסמטיים בלבד ואינם מספקים בידוד אמיתי כלל</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. כי VMs אינן זקוקות למערכת הפעלה משלהן בכלל</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Namespaces מבודדות מה כל קונטיינר "רואה" (תהליכים, רשת, mounts) ו-Cgroups מגבילות משאבים - אבל שתי הטכנולוגיות פועלות מעל אותו kernel משותף למארח ולכל הקונטיינרים. VM, לעומת זאת, מריצה kernel מלא ונפרד משלה מעל שכבת Hypervisor, כך שגם פגיעה חמורה בתוך אורח אחד לא חושפת ישירות את המארח או אורחים אחרים. זו הסיבה שקונטיינרים נחשבים לבידוד "קל" (lightweight isolation) ו-VMs לבידוד "חזק" (strong isolation).</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>6. מה קורה כאשר קונטיינר שרץ כחלק מ-Swarm service מוגדר עם <code>HEALTHCHECK</code> ב-Dockerfile, וה-health check שלו מתחיל להחזיר <code>unhealthy</code> שוב ושוב?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Docker Swarm מתעלם לחלוטין מסטטוס ה-health check ולא נוקט שום פעולה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Swarm מזהה את המשימה (task) כ-unhealthy, הורג אותה ומתזמן מחדש task חדש כתחליף (בכפוף ל-restart policy של ה-service) - וכן, סטטוס health משפיע ישירות על ניהול rolling update, כך שאם עדכון גורם ל-unhealthy, ניתן לגרום ל-rollback אוטומטי</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. ה-health check רלוונטי רק לפלט של <code>docker ps</code> ואין לו שום השפעה תפעולית מעבר לתצוגה</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. הקונטיינר יימחק לצמיתות מה-cluster ולעולם לא יופעל מחדש, גם לא ידנית</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> <code>HEALTHCHECK</code> מגדיר פקודה שרצה מעת לעת בתוך הקונטיינר; הסטטוס שלה (<code>healthy</code>/<code>unhealthy</code>/<code>starting</code>) לא נשאר רק קוסמטי - ב-Swarm mode, task שהופך ל-unhealthy נחשב כושל ומוחלף אוטומטית בהתאם ל-restart policy של ה-service. בנוסף, בזמן <code>service update</code>, אם הגדרתם <code>update_config</code> עם <code>failure_action: rollback</code>, כישלון health check במהלך הפריסה יכול לגרום ל-Swarm לבצע rollback אוטומטי לגרסה הקודמת.</div>
</div>

<div class="quiz-card" data-answer="ב">

</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>8. מה ההבדל בין <code>always</code> ל-<code>unless-stopped</code> כ-Restart Policy לקונטיינר, במיוחד מבחינת ההתנהגות אחרי הפעלה מחדש (restart) של ה-Docker daemon או המארח?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין שום הבדל בין השתיים בשום מקרה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. שתיהן מפעילות מחדש את הקונטיינר תמיד, גם אם הוא נעצר ידנית עם <code>docker stop</code>, ללא יוצא מן הכלל</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. עם <code>always</code>, הקונטיינר יופעל מחדש אחרי restart של ה-daemon/המארח - גם אם נעצר ידנית לפני כן; עם <code>unless-stopped</code>, הקונטיינר יופעל מחדש אוטומטית אחרי restart של ה-daemon, אבל רק אם הוא לא נעצר ידנית (<code>docker stop</code>) לפני כן - כלומר עצירה ידנית "נזכרת" ולא מפעילה מחדש את הקונטיינר אחרי אתחול</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>unless-stopped</code> אף פעם לא מפעיל מחדש קונטיינר, גם לא אחרי קריסה</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> זו נקודה עדינה שקל להתבלבל בה - שתי המדיניות דומות מאוד בהתנהגות היומיומית (שתיהן מפעילות מחדש קונטיינר שקרס), אבל נבדלות בדיוק במקרה של restart למערכת: <code>always</code> "שוכח" שהמשתמש עצר את הקונטיינר ידנית ומפעיל אותו מחדש בכל מקרה; <code>unless-stopped</code> זוכר את הכוונה המפורשת של המשתמש לעצור, ולא יפעיל את הקונטיינר מחדש לאחר אתחול אם הוא היה במצב "עצור ידנית" לפני כן.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>9. כשקונטיינר חורג ממגבלת הזיכרון שהוגדרה לו (<code>--memory</code>), מה קורה בפועל בלינוקס?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Docker מגדיל אוטומטית את המגבלה כדי למנוע כל בעיה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. ה-CPU של הקונטיינר מוגבל אוטומטית לפיצוי, אך צריכת הזיכרון בפועל אף פעם לא נחסמת</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. ה-OOM Killer (Out Of Memory Killer) של ה-kernel יהרוג (SIGKILL) את התהליך החורג בתוך הקונטיינר, בדרך כלל התהליך הראשי (PID 1); הקונטיינר ייצא עם קוד יציאה 137 (128+9, מציין SIGKILL), ואם הוגדרה Restart Policy מתאימה הוא עשוי לעלות מחדש - אך כל הנתונים שהיו בזיכרון אבדים</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. הקונטיינר עובר אוטומטית למצב read-only קבוע עד להפעלה מחדש ידנית</button>

<script>
(function () {
  function initQuiz() {
    var cards = document.querySelectorAll('.quiz-card');
    var scoreEl = document.getElementById('quiz-score');
    var resetAllBtn = document.getElementById('quiz-reset-all');

    function updateScore() {
      if (!scoreEl) return;
      var correctCount = document.querySelectorAll('.quiz-card--answered[data-was-correct="true"]').length;
      scoreEl.textContent = 'ענית נכון על ' + correctCount + ' מתוך ' + cards.length;
    }

    function answerCard(card, chosenBtn) {
      var correct = card.getAttribute('data-answer');
      var chosen = chosenBtn.getAttribute('data-choice');
      var isCorrect = chosen === correct;

      card.classList.add('quiz-card--answered');
      card.setAttribute('data-was-correct', isCorrect ? 'true' : 'false');

      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = true;
        if (opt.getAttribute('data-choice') === correct) {
          opt.classList.add('quiz-option--correct');
        } else if (opt === chosenBtn) {
          opt.classList.add('quiz-option--incorrect');
        }
      });

      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = isCorrect ? '✅ נכון!' : '❌ לא נכון - התשובה הנכונה מסומנת בירוק.';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
        result.classList.add(isCorrect ? 'quiz-result--correct' : 'quiz-result--incorrect');
      }

      updateScore();
    }

    function resetCard(card) {
      card.classList.remove('quiz-card--answered');
      card.removeAttribute('data-was-correct');
      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = false;
        opt.classList.remove('quiz-option--correct', 'quiz-option--incorrect');
      });
      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = '';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
      }
    }

    cards.forEach(function (card) {
      card.querySelectorAll('.quiz-option').forEach(function (btn) {
        btn.addEventListener('click', function () {
          if (card.classList.contains('quiz-card--answered')) return;
          answerCard(card, btn);
        });
      });
    });

    if (resetAllBtn) {
      resetAllBtn.addEventListener('click', function () {
        cards.forEach(resetCard);
        updateScore();
      });
    }

    updateScore();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initQuiz);
  } else {
    initQuiz();
  }
})();
</script>
