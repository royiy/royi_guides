שאלות חזרה אינטראקטיביות המסכמות את כל מדריכי ה-Docker שלמדתם - החל מהמושגים הבסיסיים (Image, Container, Namespaces, cgroups), דרך אבטחה, Volumes, Networking ו-Docker Compose, וכלה ב-Docker Swarm ופרודקשן. בחרו תשובה בכל שאלה ותקבלו מיד משוב האם היא נכונה, יחד עם הסבר.

<div id="quiz-score" class="quiz-score">ענית נכון על 0 מתוך 10</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>1. מהו ההבדל המרכזי בין Namespaces ל-Cgroups, שתי הטכנולוגיות שעליהן מבוסס Docker בלינוקס?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Namespaces מגבילות כמות זיכרון ו-CPU, ו-Cgroups מבודדות רשת בלבד</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Namespaces מבודדות את מה שהתהליך "רואה" (מערכת קבצים, רשת, PIDs, משתמשים), ו-Cgroups מגבילות ומנהלות כמה משאבים (CPU, זיכרון, דיסק) התהליך יכול לצרוך</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. שתיהן עושות בדיוק אותו דבר, ומטרתן היא רק תאימות לאחור</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Namespaces רצות רק ב-Windows, ו-Cgroups רק ב-Linux</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Docker "עוטף" בממשק נוח שתי טכנולוגיות ליבה של לינוקס: Namespaces מבודדות מה כל קונטיינר יכול לראות (כך שהוא "חושב" שהוא לבד במערכת), ו-Control Groups (cgroups) קובעות כמה משאבי חומרה כל קונטיינר מותר לו לצרוך.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>2. למה הוספת משתמש לקבוצת <code>docker</code> בלינוקס (כדי להריץ פקודות בלי <code>sudo</code>) נחשבת בפועל שקולה למתן הרשאות root?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. זה לא נכון - קבוצת docker מוגבלת לחלוטין ואינה מהווה סיכון אבטחה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. כי המשתמש מקבל אוטומטית סיסמת root חדשה</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. כי כל מי שבקבוצה יכול להריץ קונטיינר עם גישה מלאה למערכת הקבצים של המארח (למשל mount של <code>/</code>), ולכן זו למעשה שליטה מלאה על השרת</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. כי חברי הקבוצה יכולים לשנות את סיסמת המשתמשים האחרים במערכת ההפעלה</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ה-Docker daemon רץ כ-root, ומי שנמצא בקבוצת docker יכול לתקשר איתו ולהריץ קונטיינרים עם הרשאות מלאות - כולל mount של כל מערכת הקבצים של המארח לתוך קונטיינר. זו שאלת אבטחה קלאסית בראיונות עבודה.</div>
</div>

<div class="quiz-card" data-answer="א">
  <p class="quiz-question"><strong>3. מה ההבדל בין <code>docker stop</code> ל-<code>docker kill</code>?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. <code>stop</code> שולח SIGTERM ומחכה (ברירת מחדל כ-10 שניות) לפני שהוא שולח SIGKILL בכוח; <code>kill</code> שולח SIGKILL מיידית וברוטלית</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. <code>stop</code> מוחק את הקונטיינר לצמיתות, ו-<code>kill</code> רק משהה אותו זמנית</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. אין הבדל מעשי בין השתיים</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>kill</code> עובד רק על קונטיינרים שרצים ברקע (<code>-d</code>), ו-<code>stop</code> רק על קונטיינרים אינטראקטיביים</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> <code>docker stop</code> מבצע עצירה "חינה" - שולח SIGTERM כדי לתת לתהליך הזדמנות לסגור את עצמו בעדינות, ורק אם הוא לא מגיב בזמן שולח SIGKILL. <code>docker kill</code> שולח SIGKILL באופן מיידי, בלי הזדמנות לסגירה מסודרת.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>4. מהי המטרה העיקרית של Multi-stage Builds ב-Dockerfile?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. להריץ את אותו Dockerfile על כמה מערכות הפעלה שונות במקביל</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. להשתמש בכמה שלבי בנייה נפרדים, כשרק התוצר הסופי (למשל בינארי מקומפל) עובר ל-image הסופי - כך ה-image לא כולל כלי build, קוד מקור ותלויות פיתוח, וגודלו מצטמצם דרסטית</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. לאפשר להריץ כמה קונטיינרים שונים מאותו image בו-זמנית</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. להחליף את הצורך ב-<code>docker-compose.yml</code> לחלוטין</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> דוגמה קלאסית היא אפליקציית Go: שלב אחד (<code>FROM golang AS builder</code>) בונה בינארי, ושלב שני מעתיק רק את הבינארי (<code>COPY --from=builder</code>) ל-image מינימלי כמו <code>alpine</code> - כך image שהיה יכול לשקול מאות מגה-בייטים מצטמצם למגה-בייטים בודדים.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>5. למה חשיפת <code>/var/run/docker.sock</code> לתוך קונטיינר (למשל בכלי CI/CD) נחשבת מסוכנת במיוחד?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. זה מאט את ביצועי הקונטיינר משמעותית, אך לא מהווה סיכון אבטחה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. זה חוסם את הקונטיינר מגישה לאינטרנט</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. זה נותן לקונטיינר שליטה מלאה על ה-Docker daemon, שיכול ליצור קונטיינרים חדשים עם הרשאות מלאות על המארח - בפועל שקול ל-root access על השרת</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. זה מונע מהקונטיינר לגשת ל-volumes משותפים</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> מי ששולט ב-Docker socket יכול להורות ל-daemon ליצור קונטיינר חדש עם, למשל, mount של כל מערכת הקבצים של המארח - ולכן חשיפת ה-socket שקולה למתן הרשאות root מלאות. פתרונות מקלים כוללים Docker socket proxy עם הרשאות מוגבלות או הרצה ב-rootless mode.</div>
</div>

<div class="quiz-card" data-answer="א">
  <p class="quiz-question"><strong>6. מה קורה לנתונים שנכתבים בתוך קונטיינר, אם לא הוגדר עבורם Volume או Bind Mount, וברגע נתון מוחקים את הקונטיינר?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. הם נמחקים לצמיתות - קונטיינרים הם Ephemeral (בני חלוף) כברירת מחדל</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. הם נשמרים אוטומטית ב-Docker Hub</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. הם עוברים אוטומטית ל-Image המקורי שממנו נוצר הקונטיינר</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Docker שולח אזהרה ומונע את מחיקת הקונטיינר עד שהנתונים יגובו</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> זו בדיוק הבעיה ש-Volumes, Bind Mounts ו-tmpfs נועדו לפתור. בלי אחד מהם, כל נתון שנכתב בקונטיינר (כמו קבצי דאטהבייס) נמחק ברגע שהקונטיינר עצמו נמחק - ולכן לדאטהבייסים ותוכן קבוע תמיד צריך Volume ייעודי.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>7. מהו היתרון המרכזי של רשת bridge מותאמת אישית (<code>docker network create</code>) לעומת רשת ה-default bridge?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. היא תמיד מהירה יותר פי 10 מרשת ה-default</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. היא מספקת DNS resolution אוטומטי - קונטיינרים יכולים למצוא אחד את השני לפי שם (למשל <code>postgresql://database:5432</code>), בלי צורך ב-<code>--link</code> המיושן</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. רק ברשת מותאמת אישית אפשר למפות פורטים עם <code>-p</code></button>
    <button class="quiz-option" type="button" data-choice="ד">ד. רשת מותאמת אישית לא תומכת יותר משני קונטיינרים בו-זמנית</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ברשת ה-default bridge אין DNS resolution אוטומטי בין קונטיינרים - היה צריך את הדגל הישן <code>--link</code>. ברשת user-defined, אפשר פשוט לגשת לקונטיינר אחר לפי שמו (למשל <code>backend</code> ניגש ל-<code>database</code> ישירות), מה שהופך אותה לבחירת ברירת המחדל המומלצת בפועל.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>8. מהי המגבלה של <code>depends_on</code> הבסיסי ב-Docker Compose, ואיך פותרים אותה?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. הוא לא נתמך יותר בגרסאות חדשות של Compose ויש להשתמש רק ב-<code>links</code></button>
    <button class="quiz-option" type="button" data-choice="ב">ב. הוא עובד רק עם שני שירותים לכל היותר</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. הוא רק מוודא שהקונטיינר "התחיל" לרוץ, לא שהשירות בפועל "מוכן" לקבל תעבורה; פותרים זאת בשילוב עם <code>healthcheck</code> והתנאי <code>condition: service_healthy</code></button>
    <button class="quiz-option" type="button" data-choice="ד">ד. הוא מונע מהשירותים לשתף רשת משותפת</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> דוגמה טיפוסית: שירות <code>web</code> תלוי ב-<code>db</code>, אבל דאטהבייס עדיין נמצא באתחול כשה-container "עלה". הפתרון הוא להגדיר <code>healthcheck</code> על ה-db (כמו <code>pg_isready</code>) ולציין ב-web <code>depends_on: db: condition: service_healthy</code>, כך שה-web ימתין עד שהדאטהבייס באמת מוכן.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>9. למה מומלץ להשתמש במספר אי-זוגי של Manager nodes (1, 3, 5) ב-Docker Swarm?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. כי Docker לא תומך טכנית ביותר מ-5 managers</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. כי Swarm משתמש באלגוריתם Raft consensus שדורש רוב (majority) כדי לקבל החלטות; מספר אי-זוגי מונע מצב "תיקו" ומאפשר לסבול נפילה של עד (n-1)/2 managers מבלי לאבד quorum</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. כי כל manager נוסף מכפיל את מהירות ה-Load Balancing</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. זו רק המלצת עיצוב שאין לה השפעה טכנית בפועל</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Managers ב-Swarm מסכימים על מצב ה-cluster באמצעות Raft, שדורש רוב תקין כדי לפעול. עם 3 managers, ה-cluster ממשיך לתפקד גם אם manager אחד נופל (עדיין יש רוב של 2 מתוך 3); מספר זוגי לא מוסיף שום יתרון נוסף בעמידות אבל מגדיל את הסיכון ל"תיקו".</div>
</div>

<div class="quiz-card" data-answer="א">
  <p class="quiz-question"><strong>10. למה מומלץ בפרודקשן להימנע משימוש בתגית <code>latest</code> עבור Images (בין אם ב-<code>docker run</code>, ב-<code>FROM</code> בתוך Dockerfile, או ב-service update)?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. כי <code>latest</code> אינו בהכרח הגרסה היציבה ביותר והוא עלול להשתנות "מתחתיכם" בלי אזהרה - לכן עדיף לקבע תמיד גרסה ספציפית וידועה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. כי תגית <code>latest</code> תמיד כבדה יותר בגודל מכל תגית אחרת</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. כי Docker Hub חוסם הורדה של images עם תגית <code>latest</code> בחשבונות חינמיים</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. כי <code>latest</code> עובד רק על מערכת ההפעלה Windows</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> אם לא מציינים tag, Docker מניח <code>latest</code> כברירת מחדל - אבל זהו סתם שם נפוץ למי שפרסם אחרון, לא אינדיקציה ליציבות. שימוש בגרסה מפורשת (כמו <code>nginx:1.25.3</code>) מבטיח שכל סביבה (dev, staging, production) תריץ בדיוק אותו קוד, ומונע הפתעות מגרסה חדשה שהתפרסמה בטעות תחת <code>latest</code>.</div>
</div>

    function updateScore() {
      if (!scoreEl) return;
      var correctCount = document.querySelectorAll('.quiz-card--answered[data-was-correct="true"]').length;
      scoreEl.textContent = 'ענית נכון על ' + correctCount + ' מתוך ' + cards.length;
    }

    function answerCard(card, chosenBtn) {
      var correct = card.getAttribute('data-answer');
      var chosen = chosenBtn.getAttribute('data-choice');
      var isCorrect = chosen === correct;

      card.classList.add('quiz-card--answered');
      card.setAttribute('data-was-correct', isCorrect ? 'true' : 'false');

      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = true;
        if (opt.getAttribute('data-choice') === correct) {
          opt.classList.add('quiz-option--correct');
        } else if (opt === chosenBtn) {
          opt.classList.add('quiz-option--incorrect');
        }
      });

      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = isCorrect ? '✅ נכון!' : '❌ לא נכון - התשובה הנכונה מסומנת בירוק.';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
        result.classList.add(isCorrect ? 'quiz-result--correct' : 'quiz-result--incorrect');
      }

      updateScore();
    }

    function resetCard(card) {
      card.classList.remove('quiz-card--answered');
      card.removeAttribute('data-was-correct');
      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = false;
        opt.classList.remove('quiz-option--correct', 'quiz-option--incorrect');
      });
      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = '';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
      }
    }

    cards.forEach(function (card) {
      card.querySelectorAll('.quiz-option').forEach(function (btn) {
        btn.addEventListener('click', function () {
          if (card.classList.contains('quiz-card--answered')) return;
          answerCard(card, btn);
        });
      });
    });

    if (resetAllBtn) {
      resetAllBtn.addEventListener('click', function () {
        cards.forEach(resetCard);
        updateScore();
      });
    }

    updateScore();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initQuiz);
  } else {
    initQuiz();
  }
})();
</script>
