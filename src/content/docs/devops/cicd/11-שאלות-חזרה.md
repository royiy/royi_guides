שאלות חזרה אינטראקטיביות על כל מה שלמדתם לאורך מדריכי ה-CI/CD (מושגי יסוד, Git ואסטרטגיות ענפים, Jenkins, GitHub Actions, GitLab CI/CD, Docker, Kubernetes ו-Continuous Deployment, אוטומציית בדיקות, Terraform ו-Infrastructure as Code, ו-DevSecOps). בחרו תשובה בכל שאלה ותקבלו מיד משוב האם היא נכונה, יחד עם הסבר.

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>1. מה ההבדל העיקרי בין Continuous Delivery ל-Continuous Deployment?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין הבדל, אלו שני שמות לאותו תהליך</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. ב-Delivery כל שינוי שעובר CI מוכן לפריסה אך דורש אישור ידני לפרודקשן, ואילו ב-Deployment הפריסה לפרודקשן אוטומטית לחלוטין ללא התערבות אדם</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. Delivery מתייחס רק ל-build, ו-Deployment רק ל-testing</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Deployment דורש אישור ידני, ו-Delivery אוטומטי לגמרי</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Continuous Delivery אומר שכל שינוי שעבר את שלב ה-CI מוכן טכנית לפריסה, אך הפריסה בפועל לפרודקשן דורשת Manual Approval. Continuous Deployment הולך צעד נוסף - כל שינוי שעובר את כל שלבי הבדיקה נפרס אוטומטית, ללא מגע יד אדם.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>2. מהי הגישה של Trunk-Based Development, ומה מאפשר לפי המדריך למזג קוד לא-גמור ל-<code>main</code> בבטחה?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. עבודה על ענפי <code>release/*</code> ארוכי חיים עם מיזוג בסוף כל רבעון</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. חסימת push לגמרי ל-<code>main</code> עד לסיום כל הפיצ'רים</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. עבודה ישירה (או עם branches קצרי חיים) על <code>main</code>, כאשר Feature Flags מסתירים פיצ'רים לא-גמורים בפרודקשן</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. שימוש ב-<code>git stash</code> כדי להסתיר קוד לא גמור לפני כל push</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ב-Trunk-Based Development כולם עובדים ישירות (או עם branches קצרי חיים של שעות) על <code>main</code>/<code>trunk</code>. Feature Flags מנתקים בין "Deploy" ל-"Release" - כך אפשר למזג קוד לא-גמור ל-<code>main</code> בבטחה, מאחורי flag כבוי, וזהו הבסיס למודל Continuous Deployment אמיתי בחברות כמו Google ו-Facebook.</div>
</div>

<div class="quiz-card" data-answer="א">
  <p class="quiz-question"><strong>3. מה ההבדל בין Declarative ל-Scripted Pipeline ב-Jenkins?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Declarative הוא syntax מובנה ומחמיר (<code>pipeline { stages { ... } }</code>), קל יותר לקריאה ותחזוקה; Scripted הוא Groovy גמיש לחלוטין, נותן שליטה מלאה אך מסובך יותר ודורש ידע ב-Groovy</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Declarative רץ רק על Windows agents, ו-Scripted רק על Linux agents</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. Scripted הוא הסינטקס החדש והמומלץ שהחליף לגמרי את Declarative</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. אין הבדל מעשי בין השניים, זו רק שאלה של העדפה ויזואלית</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Declarative Pipeline (עם בלוק <code>pipeline { agent ... stages { ... } }</code>) הוא הגישה המובנית והנפוצה יותר היום. Scripted Pipeline (מבוסס <code>node { stage(...) { ... } }</code>) הוא הגישה הישנה יותר, כתובה כקוד Groovy חופשי - גמישה מאוד אך דורשת ידע תכנותי מעמיק יותר.</div>
</div>

<div class="quiz-card" data-answer="ד">
  <p class="quiz-question"><strong>4. מה תפקידו של המפתח <code>needs</code> בעבודה עם Jobs ב-GitHub Actions?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. מגדיר אילו secrets ה-job צריך כדי לרוץ</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. קובע על איזה runner (ubuntu/windows/macos) ה-job ירוץ</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. מגדיר cache לתלויות בין הרצות שונות</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. יוצר תלות סדר בין jobs - שכברירת מחדל רצים במקביל - כך ש-job מסוים ירוץ רק אחרי שה-job שצוין הצליח</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ב-GitHub Actions כל ה-jobs רצים במקביל כברירת מחדל. כדי ליצור סדר (למשל שה-<code>deploy</code> ירוץ רק אחרי ש-<code>build-and-push</code> הצליח, וזה רק אחרי ש-<code>test</code> הצליח) יש להשתמש במפתח <code>needs: [job-name]</code>.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>5. מהו ההבדל בין <code>rules</code> ל-<code>only</code>/<code>except</code> ב-GitLab CI/CD?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. <code>only</code>/<code>except</code> הוא הסינטקס החדש שמחליף את <code>rules</code></button>
    <button class="quiz-option" type="button" data-choice="ב">ב. <code>rules</code> הוא הסינטקס המודרני והגמיש יותר, התומך בתנאים מורכבים (<code>if</code>, <code>changes</code>, <code>exists</code>) ומחליף בפועל את <code>only</code>/<code>except</code> הישן שכיום deprecated</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. שניהם זהים לחלוטין מבחינה תפקודית, ההבדל רק בשם</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>rules</code> משמש רק להגדרת Runners, ולא לתנאי הרצת jobs</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> <code>rules</code> הוא ה-syntax המודרני והגמיש יותר לקביעה מתי job ירוץ, ומאפשר לשלב תנאים מרובים (כמו <code>if: '$CI_COMMIT_BRANCH == "main"'</code>), בדיקת <code>changes</code> לפי קבצים ששונו, ו-<code>when: manual</code> - והוא מחליף את <code>only</code>/<code>except</code> הישן יותר.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>6. למה חשוב Multi-Stage Build ב-Dockerfile במסגרת פייפליין CI/CD?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. הוא מאיץ את ה-CPU בזמן ריצת הקונטיינר בפרודקשן</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. הוא היחיד שמאפשר לתייג image עם Git SHA</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. הוא מפריד בין סביבת הבנייה (כלי build, devDependencies) לסביבת הריצה, כך שה-image הסופי לא מכיל את כלי הבנייה - קטן יותר, מאובטח יותר ומהיר יותר לפרוס</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. הוא מבטל את הצורך ב-<code>.dockerignore</code></button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ב-Multi-Stage Build יש שלב <code>builder</code> שמכיל את כלי הבנייה (למשל <code>npm ci</code> ו-<code>npm run build</code>), ושלב <code>production</code> נפרד שמעתיק אליו רק את פלט הבנייה. כך ה-image הסופי נטול כלי בנייה מיותרים, קטן, מאובטח ומהיר יותר לפרוס.</div>
</div>

<div class="quiz-card" data-answer="א">
  <p class="quiz-question"><strong>7. מה ההבדל בין Blue-Green Deployment ל-Canary Deployment ב-Kubernetes?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Blue-Green מעביר 100% מהתעבורה בבת אחת בין שתי סביבות זהות (rollback מיידי, אך דורש כפול משאבים); Canary מעביר אחוז הולך וגדל מהתעבורה בהדרגה תוך ניטור מטריקות</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Canary מעביר 100% מהתעבורה בבת אחת, ו-Blue-Green מעביר אחוזים הדרגתיים</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. שתי האסטרטגיות זהות לחלוטין, ההבדל הוא רק בשם שנותנים להן</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Blue-Green רלוונטי רק ל-Jenkins, ו-Canary רלוונטי רק ל-GitHub Actions</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ב-Blue-Green יש שתי סביבות זהות ("Blue" הישנה ו-"Green" החדשה) ומעבירים את כל התעבורה בבת אחת מ-Blue ל-Green ברגע שהיא מאומתת - rollback מיידי אך דורש כפול משאבים. ב-Canary שולחים תחילה אחוז קטן (5%-10%) מהתעבורה לגרסה החדשה, בודקים מטריקות, ורק אז מגדילים בהדרגה ל-100%.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>8. מה ממליצה "פירמידת הבדיקות" (Test Pyramid) על התפלגות סוגי הבדיקות בפייפליין CI/CD?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. רוב הבדיקות צריכות להיות E2E, כי הן בודקות את הזרימה המלאה של המשתמש</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. רוב הבדיקות צריכות להיות Unit Tests (מהירות וזולות), פחות Integration Tests, ומעט מאוד E2E Tests (איטיות ויקרות)</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. יש להריץ אך ורק Integration Tests, ולוותר לגמרי על Unit ו-E2E</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. כמות הבדיקות בכל שכבה צריכה להיות זהה בדיוק</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> פירמידת הבדיקות ממליצה על בסיס רחב של הרבה Unit Tests מהירות ומבודדות, שכבת ביניים בינונית של Integration Tests, וקצה צר של מעט E2E Tests שהן איטיות, יקרות ושבריריות יותר. זה מנחה בניית pipeline שמקבל פידבק מהיר משכבת ה-unit, וה-E2E האיטי רץ רק כשצריך.</div>
</div>

<div class="quiz-card" data-answer="ג">

  <div class="quiz-options">

    <button class="quiz-option" type="button" data-choice="ג">ג. ה-CI מריץ <code>terraform plan</code> על כל PR ומפרסם את התוצאה לסקירה בתגובה, ורק אחרי אישור ומיזוג ל-<code>main</code> ה-CI מריץ <code>terraform apply</code> בפועל</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>plan</code> ו-<code>apply</code> מיועדים אך ורק להרצה ידנית מהמחשב האישי, ולא מ-pipeline</button>

<script>
(function () {
  function initQuiz() {
    var cards = document.querySelectorAll('.quiz-card');
    var scoreEl = document.getElementById('quiz-score');
    var resetAllBtn = document.getElementById('quiz-reset-all');

    function updateScore() {
      if (!scoreEl) return;
      var correctCount = document.querySelectorAll('.quiz-card--answered[data-was-correct="true"]').length;
      scoreEl.textContent = 'ענית נכון על ' + correctCount + ' מתוך ' + cards.length;
    }

    function answerCard(card, chosenBtn) {
      var correct = card.getAttribute('data-answer');
      var chosen = chosenBtn.getAttribute('data-choice');
      var isCorrect = chosen === correct;

      card.classList.add('quiz-card--answered');
      card.setAttribute('data-was-correct', isCorrect ? 'true' : 'false');

      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = true;
        if (opt.getAttribute('data-choice') === correct) {
          opt.classList.add('quiz-option--correct');
        } else if (opt === chosenBtn) {
          opt.classList.add('quiz-option--incorrect');
        }
      });

      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = isCorrect ? '✅ נכון!' : '❌ לא נכון - התשובה הנכונה מסומנת בירוק.';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
        result.classList.add(isCorrect ? 'quiz-result--correct' : 'quiz-result--incorrect');
      }

      updateScore();
    }

    function resetCard(card) {
      card.classList.remove('quiz-card--answered');
      card.removeAttribute('data-was-correct');
      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = false;
        opt.classList.remove('quiz-option--correct', 'quiz-option--incorrect');
      });
      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = '';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
      }
    }

    cards.forEach(function (card) {
      card.querySelectorAll('.quiz-option').forEach(function (btn) {
        btn.addEventListener('click', function () {
          if (card.classList.contains('quiz-card--answered')) return;
          answerCard(card, btn);
        });
      });
    });

    if (resetAllBtn) {
      resetAllBtn.addEventListener('click', function () {
        cards.forEach(resetCard);
        updateScore();
      });
    }

    updateScore();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initQuiz);
  } else {
    initQuiz();
  }
})();
</script>
