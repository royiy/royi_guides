זהו מדריך המסכם - ריכוז של השאלות הנפוצות ביותר בראיונות Terraform, מסודרות לפי רמת קושי, בתוספת טיפים מתקדמים שמפרידים בין "מכיר את הבסיס" ל"מומחה בפועל".

---

## חלק א': שאלות בסיסיות (Junior)

**1. מה זה Terraform ולמה הוא נחשב Infrastructure as Code?**
כלי open-source מבית HashiCorp המאפשר להגדיר תשתית ענן/מקומית בקבצי תצורה declarative (HCL), לגרסא אותם בגיט, ולנהל את מחזור החיים המלא (create/update/destroy) בצורה עקבית וחוזרת (idempotent).

**2. מה ההבדל בין Terraform לכלים כמו CloudFormation או Pulumi?**
CloudFormation הוא ספציפי ל-AWS בלבד; Terraform הוא multi-cloud (AWS/Azure/GCP/K8s/ועוד מאות providers). Pulumi מאפשר לכתוב תשתית בשפות תכנות רגילות (TypeScript/Python) במקום DSL ייעודי כמו HCL - Terraform מציע יותר סטנדרטיזציה ופשטות, Pulumi מציע יותר גמישות תכנותית.

**3. הסבירו את שלושת שלבי ה-workflow הבסיסי.**
Write (כתיבת קוד) → Plan (חישוב שינויים נדרשים) → Apply (ביצוע בפועל).

**4. מה זה provider?**
פלאגין שמתרגם בלוקים ב-HCL לקריאות API בפועל לשירות חיצוני (AWS, Azure וכו').

**5. מה ההבדל בין `resource` ל-`data source`?**
`resource` יוצר/מנהל משאב; `data` רק קורא מידע קיים בלי לשנות אותו.

**6. מה קורה כשמריצים `terraform destroy`?**
Terraform מוחק את **כל** המשאבים המתועדים ב-state, לפי סדר הפוך מהיצירה (מכבד תלויות).

**7. איך מזינים ערך למשתנה?**
CLI flag (`-var`), קובץ `terraform.tfvars`, `*.auto.tfvars`, משתני סביבה (`TF_VAR_*`), או `default` בהגדרת המשתנה.

## חלק ב': שאלות ביניים (Mid-level)

**8. מה זה Terraform state ולמה זה כל כך קריטי?**
קובץ JSON שממפה בין הקונפיגורציה למשאבים בפועל בענן - ה"מקור אמת" של Terraform. בלעדיו אין דרך לדעת מה קיים, אילו IDs יש למשאבים ומה התלויות ביניהם.

**9. איך פותרים בעיית עבודת צוות עם state?**
Remote backend (S3/Azure Blob/GCS/Terraform Cloud) + state locking (DynamoDB ל-S3, native ל-Terraform Cloud) כדי למנוע מירוצים והבטיח מקור אמת יחיד.

**10. מה ההבדל בין `count` ל-`for_each`, ומתי תעדיפו כל אחד?**
`count` - מבוסס אינדקס מספרי, פשוט אבל שביר כשמסירים פריט מהאמצע (משנה את כל האינדקסים שאחריו → destroy/recreate מיותר). `for_each` - מבוסס מפתח ייחודי (set/map), יציב יותר לשינויים. כלל אצבע: אם הרשימה עלולה להשתנות באמצע, תמיד `for_each`.

**11. מה זה module ומתי כדאי ליצור אחד?**
אוסף קבצי `.tf` לשימוש חוזר. כדאי כשיש קוד שחוזר על עצמו בכמה מקומות (למשל VPC בסטנדרט קבוע), או כשרוצים להסתיר מורכבות מאחורי interface נקי (variables/outputs).

**12. איך מתמודדים עם drift (סטייה בין state למציאות)?**
מזהים עם `terraform plan` (או `plan -refresh-only` לפירוט). מתקנים על ידי `apply` (מחזיר את המציאות לתאום עם הקוד) או עדכון הקוד כך שישקף את המציאות ואז `apply -refresh-only` (מעדכן רק את ה-state).

**13. מה ההבדל בין `terraform state rm` ל-`terraform destroy`?**
`state rm` מסיר משאב מ-state בלי לגעת בו בפועל בענן (הוא ממשיך להתקיים, סתם לא מנוהל יותר). `destroy` מוחק אותו בפועל.

**14. מה זה `lifecycle` block ומה השדות המרכזיים בו?**
בלוק לשליטה על מחזור חיים של resource: `create_before_destroy` (יצירה לפני מחיקה, zero-downtime), `prevent_destroy` (הגנה מפני מחיקה בטעות), `ignore_changes` (התעלמות משינויים בשדות ספציפיים).

**15. איך Terraform בונה את סדר היצירה/מחיקה של משאבים?**
באמצעות DAG (Directed Acyclic Graph) שנבנה אוטומטית מהפניות בין משאבים בקוד. משאבים ללא תלות ביניהם נוצרים **במקביל**, מה שהופך Terraform ליעיל יחסית.

## חלק ג': שאלות מתקדמות (Senior)

**16. איך הייתם מתכננים ארכיטקטורת Terraform לארגון גדול עם עשרות צוותים?**
נקודות מפתח לתשובה טובה:
- פיצול ל-state נפרדים לפי domain (network/security/database/app) כדי להקטין blast radius
- מודולים משותפים ב-internal registry עם versioning ברור
- Policy as Code (Sentinel/OPA) לאכיפת סטנדרטים ארגוניים
- CI/CD מרכזי עם gate אישורים לפרודקשן
- ניהול הרשאות דרך IAM roles ממוקדים (לא credentials משותפים)
- תיעוד אוטומטי (`terraform-docs`) ו-linting אחיד

**17. תארו תרחיש שבו הייתם צריכים לבצע Refactor גדול ל-state בלי downtime.**
דוגמה: שינוי שם משאב או מעבר ממודול מקומי למודול חיצוני. השתמשו ב-`terraform state mv` (ולפעמים `moved` blocks בקוד עצמו מ-1.1+) כדי "להעביר" את הזיהוי ב-state בלי destroy/create:
```hcl
moved {
  from = aws_instance.web
  to   = aws_instance.app_server
}
```
זה חשוב במיוחד מ-Terraform 1.1+ - `moved` blocks נשמרים בקוד עצמו (בניגוד ל-`state mv` שהוא פקודה חד-פעמית), כך שכל מי שמריץ `apply` מקבל אוטומטית את ה-refactor בלי לזכור להריץ פקודות ידניות.

**18. איך מתמודדים עם state ענק שהופך ל-`plan`/`apply` איטיים?**
פיצול ל-state קטנים יותר לפי domain; שימוש ב-`-target` לדיבוג נקודתי (לא לשימוש קבוע); בדיקת providers מיותרים; שקילת `-parallelism` להתאמת מספר הפעולות המקבילות.

**19. מה ההבדל בין `taint`/`-replace` לבין מחיקה ידנית והרצת apply מחדש?**
`-replace` מסמן משאב ל-recreate תוך שמירה על כל התלויות וה-DAG - Terraform יודע בדיוק מה למחוק ומה ליצור ובאיזה סדר. מחיקה ידנית מהענול ישירות תיצור drift ותדרוש טיפול נוסף (refresh, ואז apply שיבנה מחדש - אבל בלי הבטחת סדר נכון אם יש תלויות מורכבות).

**20. איך הייתם מבצעים migration של backend (למשל מ-local ל-S3, או בין accounts)?**
```bash
terraform init -migrate-state
```
תוך גיבוי ידני מראש (`terraform state pull > backup.tfstate`), ווידוא ש-lock לא תפוס, ותיאום עם הצוות שאף אחד לא מריץ apply במקביל.

**21. איך מנהלים Terraform מול כמה AWS accounts/regions בו-זמנית?**
`provider` aliases (`alias = "eu"`) עם assume-role לחשבונות שונים, ו/או backend נפרד לכל חשבון/region עם state מפוצל.

**22. מה קורה כשמריצים `apply` על שינוי שדורש replace, ומה הסיכונים?**
Terraform ימחק את המשאב הישן ויצור חדש (אלא אם `create_before_destroy=true`). סיכונים: downtime, אובדן נתונים (אם אין backup), שינוי IDs/כתובות שמערכות אחרות תלויות בהם. תמיד לבדוק ב-`plan` את הסימון `-/+` לפני אישור.

**23. מה זה `terraform_data` resource ולמה הוא הוחלף ל-`null_resource`?**
`terraform_data` (מ-Terraform 1.4+) הוא resource מובנה (built-in, בלי צורך ב-provider חיצוני) שמחליף את הצורך ב-`null_resource` מ-provider ה-`null` הישן - שימושי כ"עוגן" ל-triggers ולוגיקה שלא קשורה למשאב אמיתי בענן.

**24. איך תבטיחו שקוד Terraform שלכם עמיד לשינויי גרסה של providers?**
נעיצת גרסאות (`~>`), קובץ `.terraform.lock.hcl` בגיט, בדיקות CI על גרסאות חדשות בסביבת staging לפני שדרוג פרודקשן, וקריאת CHANGELOG/Upgrade Guides לפני `init -upgrade`.

## חלק ד': שאלות תרחיש (Scenario-Based)

**25. "יצרתם משאב, מישהו מחק אותו ידנית מהקונסולה. מה קורה בהרצה הבאה?"**
`terraform plan` יזהה שהמשאב לא קיים יותר (דרך refresh) ויציע ליצור אותו מחדש (`+` create), כי ה-state עדיין "חושב" שהוא היה קיים.

**26. "צריך להוסיף 50 buckets זהים במבנה אך עם שמות שונים - איך תבנו את זה?"**
```hcl
variable "bucket_names" {
  type = list(string)
}

resource "aws_s3_bucket" "buckets" {
  for_each = toset(var.bucket_names)
  bucket   = each.value
}
```

**27. "Apply נכשל באמצע ריצה על 20 משאבים - מה עושים?"**
Terraform שומר state חלקי - כל מה שכבר נוצר בהצלחה נשאר ב-state. בודקים את הודעת השגיאה, מתקנים את הבעיה (למשל quota limit, permission), ומריצים שוב `apply` - Terraform ימשיך רק עם מה שנשאר.

**28. "צוות אחר בטעות הריץ `apply` על ה-state שלכם ושינה דברים - איך מונעים את זה מראש?"**
State locking (DynamoDB/native), הרשאות IAM ממוקדות לכל צוות/סביבה, ו/או backend נפרד לכל תחום אחריות.

**29. "צריך למחוק משאב בודד בלי לגעת בשאר התשתית."**
```bash
terraform destroy -target=aws_instance.old_server
# תמיד לעקוב עם plan מלא כדי לוודא עקביות
```
או, עדיף לרוב - להסיר את בלוק ה-resource מהקוד ולהריץ `apply` רגיל (Terraform יזהה שהוא חסר ויציע למחוק).

## טיפים וטריקים מתקדמים

### 1. `terraform console` לבדיקת expressions מסובכים לפני שכותבים בקוד
```bash
terraform console
> cidrsubnet("10.0.0.0/16", 8, 3)
"10.0.3.0/24"
```

### 2. `TF_LOG` לדיבוג עמוק
```bash
export TF_LOG=DEBUG    # TRACE, DEBUG, INFO, WARN, ERROR
export TF_LOG_PATH=./terraform.log
terraform apply
```

### 3. שימוש ב-`terraform plan -json` לעיבוד אוטומטי
```bash
terraform plan -out=tfplan
terraform show -json tfplan | jq '.resource_changes[] | select(.change.actions[0]=="delete")'
```
שימושי לבניית בדיקות CI אוטומטיות שחוסמות `apply` אם יש יותר מ-N מחיקות (הגנה מפני "עבד לי ומחק חצי מהפרודקשן").

### 4. `moved` blocks לרפקטורינג בטוח (Terraform 1.1+)
כפי שהוזכר למעלה - עדיף על `state mv` כי זה "נשאר בקוד" ולא צריך לזכור להריץ פקודה חד-פעמית שכל מפתח צריך לדעת עליה.

### 5. `removed` blocks להסרת ניהול בלי מחיקה (Terraform 1.7+)
```hcl
removed {
  from = aws_instance.legacy

  lifecycle {
    destroy = false   # מסיר מה-state בלי למחוק בפועל
  }
}
```

### 6. Precondition/Postcondition לוולידציה מתקדמת (Terraform 1.2+)
```hcl
resource "aws_instance" "web" {
  # ...
  lifecycle {
    postcondition {
      condition     = self.public_ip != ""
      error_message = "השרת חייב לקבל כתובת IP ציבורית."
    }
  }
}
```

### 7. `optional()` בהגדרת object types - שדות אופציונליים במשתנים מורכבים
```hcl
variable "server_config" {
  type = object({
    name     = string
    size     = optional(string, "t3.micro")
    replicas = optional(number, 1)
  })
}
```

### 8. שימוש ב-`terraform show -json` + `jq` לחילוץ מהיר של מידע
```bash
terraform show -json | jq '.values.root_module.resources[] | select(.type=="aws_instance") | .values.public_ip'
```

### 9. `.terraformignore` - כמו `.gitignore` אבל למודולים
מונע העלאת קבצים מיותרים כשמעלים module ל-registry פרטי.

### 10. שילוב `terraform test` בשלב CI מוקדם
לא רק ל-modules פנימיים - כתבו טסטים גם ל"חוזים" ציבוריים (למשל וידוא שמשאבים חשופים תמיד מוצפנים) לפני שהקוד מגיע ל-production branch.

## רשימת תיוג לפני ראיון (Checklist)

- [ ] יודע להסביר declarative vs imperative בדוגמה מוחשית
- [ ] יודע להבדיל בין `count` ל-`for_each` עם דוגמה לבעיה שנפתרת
- [ ] יודע להסביר state, remote backend ו-locking בביטחון
- [ ] יודע לתאר workflow שלם ב-CI/CD כולל OIDC ו-plan-before-apply
- [ ] מכיר modules - איך בונים, איך קוראים, best practices
- [ ] יודע להסביר drift ואיך מטפלים בו
- [ ] מכיר כלי אבטחה (tfsec/Checkov) ולמה הם חשובים
- [ ] יודע לענות "מה הייתם עושים אם..." על תרחישי כשל אמיתיים
- [ ] מכיר את ההבדל בין workspaces להפרדת תיקיות ומתי כל אחד מתאים
- [ ] יודע לדבר על ניהול secrets בביטחון
