מבחן אינטראקטיבי ברמת קושי גבוהה, בסגנון שאלות הסמכת **HashiCorp Certified: Terraform Associate** - בניגוד למבחן החזרה הכללי בפרק הקודם, כאן כל שאלה בודקת נקודה עדינה ומטעה שדורשת הבנה אמיתית של מנגנוני הפנים של Terraform (lifecycle, state, drift, version constraints ועוד), לא רק שינון. בחרו תשובה ותקבלו מיד משוב עם הסבר מפורט.

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>1. מהי הבעיה בשילוב <code>prevent_destroy = true</code> יחד עם <code>create_before_destroy = true</code> באותו בלוק <code>lifecycle</code>, כאשר משנים ערך שמחייב Replacement של המשאב?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין שום בעיה - Terraform יוצר את המשאב החדש ואז מוחק את הישן כרגיל</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. ה-<code>apply</code> ייכשל בשגיאה, כי <code>prevent_destroy</code> חוסם כל ניסיון מחיקה של המשאב - כולל מחיקה כחלק מתהליך Replacement</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. <code>prevent_destroy</code> מתעלם אוטומטית כש-<code>create_before_destroy</code> מוגדר</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Terraform יתעלם מהשינוי ולא יבצע דבר</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> <code>prevent_destroy</code> חוסם באופן מוחלט כל פעולת מחיקה של המשאב, ללא קשר לסיבה - גם אם המחיקה היא חלק "בריא" מתהליך Replacement עם <code>create_before_destroy</code>. השילוב הזה נראה הגיוני על הנייר אבל בפועל תוקע כל שינוי שדורש Replacement, וה-<code>apply</code> ייכשל עד שתסירו את <code>prevent_destroy</code> באופן זמני.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>2. מה <code>terraform import</code> בפועל <strong>לא</strong> עושה?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. לא מוסיף את המשאב ל-state file</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. לא מייצר עבורכם את קוד ה-HCL המתאים למשאב - אתם חייבים לכתוב את בלוק ה-<code>resource</code> בעצמכם (לפני או אחרי הייבוא) כדי שהוא יתאים למה שיובא</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. לא תומך בייבוא משאבים שכבר קיימים בענן</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. לא עובד עם רוב ה-providers הרשמיים</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> טעות נפוצה מאוד - <code>terraform import</code> רק מקשר משאב קיים בענן לרשומה ב-state file. הוא <strong>לא</strong> יוצר אוטומטית את קוד ה-HCL המתאים. אם אין כבר בלוק <code>resource</code> תואם בקוד, ה-<code>plan</code> הבא יראה "destroy" מלא כי מבחינת הקוד המשאב לא אמור להתקיים. (בגרסאות חדשות יש <code>terraform plan -generate-config-out</code> שמקל על זה, אבל זו תוספת נפרדת, לא חלק מ-<code>import</code> עצמו).</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>3. מהו ההבדל הקריטי מבחינת Blast Radius בין <code>count</code> ל-<code>for_each</code> כשמסירים פריט מהאמצע של הרשימה/המפה?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין הבדל - שתי הצורות מתנהגות זהה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. עם <code>count</code>, הסרת פריט מהאמצע גורמת לשינוי האינדקסים של כל הפריטים שאחריו ולכן ל-Destroy/Recreate מיותר שלהם; עם <code>for_each</code> (מבוסס מפתחות ייחודיים) רק המשאב שהוסר בפועל מושפע</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. עם <code>for_each</code> כל המשאבים נמחקים תמיד בכל שינוי</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>count</code> תמיד בטוח יותר לשימוש מ-<code>for_each</code></button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> משאבים עם <code>count</code> מזוהים ב-state לפי אינדקס מספרי (<code>resource[0]</code>, <code>resource[1]</code>...). הסרת איבר מהאמצע "מזיזה" את כל האינדקסים שאחריו, ו-Terraform מפרש את זה כאילו כל אותם משאבים השתנו - Destroy+Create מיותר ומסוכן. <code>for_each</code> מזהה כל משאב לפי מפתח ייחודי וקבוע (למשל שם), כך שהסרת איבר אחד משפיעה רק עליו. זו הסיבה שבפרודקשן מומלץ <code>for_each</code> על פני <code>count</code> ברשימות שעשויות להשתנות.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>4. Sentinel (Policy as Code) ב-Terraform זמין באיזו רמת מוצר?</strong></p>

    <button class="quiz-option" type="button" data-choice="ג">ג. הוחלף לחלוטין ב-OPA (Open Policy Agent) בכל הגרסאות, ו-Sentinel כבר לא קיים</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. זמין רק דרך provider חיצוני שצריך להתקין בנפרד</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> שאלה נפוצה במבחן ההסמכה - Sentinel הוא מנוע Policy-as-Code קנייני של HashiCorp, זמין רק בשכבות בתשלום של Terraform Cloud (Team & Governance ומעלה) ובTerraform Enterprise. ב-Terraform OSS פשוט אין אכיפת מדיניות מובנית; אם רוצים משהו דומה ב-OSS פונים לכלים חיצוניים כמו OPA/Conftest או Checkov.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>5. מה תפקידו של בלוק ה-<code>moved</code> שהוצג בגרסאות מודרניות יותר של Terraform?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. מזיז קבצי <code>.tf</code> פיזית בין תיקיות בפרויקט</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. מאפשר להצהיר בקוד עצמו על שינוי שם/מיקום של resource או module (למשל בזמן ריפקטור), כך ש-Terraform יבין שמדובר באותו משאב ולא יבצע Destroy+Create מיותר - חלופה מוצהרת-בקוד לפקודת <code>terraform state mv</code> הידנית</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. מעביר state בין backends שונים (למשל מ-local ל-S3)</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. מזיז תגיות (tags) בין משאבים בענן</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> לפני בלוק ה-<code>moved</code> הייתה חייבים להריץ ידנית <code>terraform state mv</code> בכל פעם שמישהו משנה שם משאב/מודול, ולזכור לתאם את זה עם כל חברי הצוות. בלוק <code>moved</code> הופך את זה לחלק דקלרטיבי מהקוד עצמו - הוא נשמר בהיסטוריית הגרסאות, וכל מי שמריץ <code>plan</code>/<code>apply</code> אחרי המשיכה מקבל את הריפקטור אוטומטית בלי Destroy+Create מיותר.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>6. אם מסמנים output כ-<code>sensitive = true</code>, מה בכל זאת נשאר חשוף?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. שום דבר - הערך מוצפן לחלוטין בכל מקום שבו הוא נשמר</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. הערך עדיין נשמר בטקסט גלוי (plaintext) בתוך ה-state file עצמו - <code>sensitive</code> רק מסתיר אותו מהפלט של ה-CLI (<code>plan</code>/<code>apply</code>/<code>output</code>), הוא לא מצפין את ה-state</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. הערך נחשף רק ל-provider הרלוונטי ולאף אחד אחר</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. אין שום קשר בין <code>sensitive</code> לתוכן ה-state file</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> זו נקודה קריטית לאבטחה שרבים מפספסים - <code>sensitive = true</code> הוא רק מנגנון תצוגה: הוא מסתיר את הערך מפלט ה-CLI כדי שלא ייחשף בלוגים של טרמינל/CI. אבל ה-state file עצמו עדיין שומר את הערך בטקסט גלוי, ולכן חובה להצפין את ה-backend (למשל S3 עם Server-Side Encryption) ולהגביל הרשאות גישה אליו.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>7. מה משמעות אילוץ הגרסה <code>~> 4.0</code> בהגדרת provider או module?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. כל גרסה מ-4.0 ומעלה, כולל 5.x ומעלה</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. גרסה 4.0 בדיוק בלבד, ללא כל עדכון</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. כל גרסה בטווח 4.x (למשל 4.1, 4.9) אך לא 5.0 ומעלה - הגבלה פסימית (pessimistic constraint) שמאפשרת עדכון רק ברכיב הימני ביותר של מספר הגרסה</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. כל גרסה נמוכה מ-4.0 בלבד</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> האופרטור <code>~></code> ("pessimistic constraint" / "twiddle-wakka") נועד לאפשר עדכוני Patch/Minor אוטומטיים בלי לסכן שינויים שוברי-תאימות (Breaking Changes) בגרסת Major. <code>~> 4.0</code> שקול ל-<code>>= 4.0, < 5.0.0</code>. שימו לב שההתנהגות משתנה בהתאם למספר הרכיבים שצוינו - <code>~> 4.1.0</code> יאפשר רק 4.1.x, בעוד <code>~> 4.1</code> יאפשר את כל 4.x.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>8. למה שימוש שגרתי ב-<code>terraform apply -target=...</code> נחשב אנטי-פטרן ומיועד רק למקרי חירום?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. הוא איטי יותר משמעותית תמיד ביחס ל-apply מלא</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. הוא מתעלם מחלק מגרף התלויות המלא, ועלול להשאיר את ה-state במצב לא עקבי ביחס למה שהיה קורה ב-<code>apply</code> מלא ורגיל</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. הוא לא נתמך יותר בגרסאות עדכניות של Terraform</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. הוא דורש הרשאות ענן מיוחדות שלא נדרשות ב-apply רגיל</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> <code>-target</code> מבצע apply על משאב ספציפי (ותלויותיו הישירות) תוך התעלמות מחלק מגרף התלויות המלא של הקונפיגורציה. שימוש חוזר בו יכול להוביל למצב state שלא תואם למה ש-apply מלא היה מייצר, ולעיתים "מסתיר" שינויים ממתינים אחרים. HashiCorp ממליצים עליו רק כפתרון זמני/חירום (למשל שחזור אחרי כשל חלקי), ולתקן מיד אחר כך עם apply מלא.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>9. מהי המגבלה המרכזית של Terraform Workspaces (<code>terraform workspace new/select</code>) כפתרון להפרדת סביבות (dev/staging/prod)?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אי אפשר להשתמש בהם כלל עם S3 backend</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. כל ה-workspaces חולקים את אותה הגדרת backend והרשאות גישה - אין בידוד אמיתי ברמת הרשאות/גישה בין הסביבות, ולכן לרוב לא מספיקים לבד כפתרון בידוד מלא ל-prod (נהוג לשלב זאת עם תיקיות/backends נפרדים)</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. workspaces תומכים רק בשתי סביבות במקביל, לא יותר</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. אי אפשר להשתמש במשתנה <code>terraform.workspace</code> בתוך הקוד</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Workspaces נוחים להפרדה קלה בין state files (למשל dev/qa) תחת אותו backend, אבל הם <strong>לא</strong> מבודדים ברמת הרשאות - כל מי שיש לו גישה ל-backend יכול לעבור בין workspaces ולגעת בכל הסביבות. לבידוד prod אמיתי (הרשאות נפרדות, blast radius מוגבל) הפרקטיקה המקובלת היא backends/תיקיות/state files נפרדים לגמרי לכל סביבה, ולא רק workspaces.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>10. מה קורה בפועל כשמריצים <code>terraform plan</code> על תשתית שסטתה (Drift) מהמצב השמור ב-state - למשל מישהו שינה ידנית הגדרה בקונסולת הענן?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. Terraform מתעלם מהשינוי הידני ולא מזהה אותו כלל, לעולם</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. Terraform מרענן (refresh) את המצב האמיתי מול הספק, משווה אותו למצב הרצוי בקוד, ומציג plan שמנסה להחזיר את המשאב למצב המוגדר בקוד - חשוב לדעת ש-Drift לא מתגלה מעצמו בלי הרצת <code>plan</code>/<code>refresh</code> יזומה</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. Terraform מוחק את המשאב אוטומטית ברגע שמזהה סטייה</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Terraform מעדכן את קוד ה-HCL בעצמו כדי להתאים אותו למצב בפועל</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> Terraform תמיד "אמת המידה" הוא הקוד המוצהר, לא המציאות בענן. כשמריצים <code>plan</code>, הוא מרענן את הידע שלו על המצב האמיתי ומשווה אל מול הקוד - וכל סטייה (Drift) תוצג כשינוי שצריך "לתקן" בחזרה למה שהקוד מגדיר. אם רוצים לגלות Drift באופן יזום בלי לחכות למישהו שירוץ plan, יש workflow ייעודי בשם <code>terraform plan -refresh-only</code>, ובTerraform Cloud יש גם Drift Detection מתוזמן.</div>
</div>

<script>
(function () {
  function initQuiz() {
    var cards = document.querySelectorAll('.quiz-card');
    var scoreEl = document.getElementById('quiz-score');
    var resetAllBtn = document.getElementById('quiz-reset-all');

    function updateScore() {
      if (!scoreEl) return;
      var correctCount = document.querySelectorAll('.quiz-card--answered[data-was-correct="true"]').length;
      scoreEl.textContent = 'ענית נכון על ' + correctCount + ' מתוך ' + cards.length;
    }

    function answerCard(card, chosenBtn) {
      var correct = card.getAttribute('data-answer');
      var chosen = chosenBtn.getAttribute('data-choice');
      var isCorrect = chosen === correct;

      card.classList.add('quiz-card--answered');
      card.setAttribute('data-was-correct', isCorrect ? 'true' : 'false');

      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = true;
        if (opt.getAttribute('data-choice') === correct) {
          opt.classList.add('quiz-option--correct');
        } else if (opt === chosenBtn) {
          opt.classList.add('quiz-option--incorrect');
        }
      });

      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = isCorrect ? '✅ נכון!' : '❌ לא נכון - התשובה הנכונה מסומנת בירוק.';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
        result.classList.add(isCorrect ? 'quiz-result--correct' : 'quiz-result--incorrect');
      }

      updateScore();
    }

    function resetCard(card) {
      card.classList.remove('quiz-card--answered');
      card.removeAttribute('data-was-correct');
      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = false;
        opt.classList.remove('quiz-option--correct', 'quiz-option--incorrect');
      });
      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = '';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
      }
    }

    cards.forEach(function (card) {
      card.querySelectorAll('.quiz-option').forEach(function (btn) {
        btn.addEventListener('click', function () {
          if (card.classList.contains('quiz-card--answered')) return;
          answerCard(card, btn);
        });
      });
    });

    if (resetAllBtn) {
      resetAllBtn.addEventListener('click', function () {
        cards.forEach(resetCard);
        updateScore();
      });
    }

    updateScore();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initQuiz);
  } else {
    initQuiz();
  }
})();
</script>
