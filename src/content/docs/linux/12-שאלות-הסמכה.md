מבחן אינטראקטיבי ברמת קושי גבוהה, בסגנון שאלות הסמכת **Red Hat Certified System Administrator (RHCSA)** - בניגוד למבחן החזרה הכללי בפרק הקודם, כאן כל שאלה בודקת נקודה עדינה ומטעה שדורשת הבנה אמיתית של מנגנוני הפנים של המערכת (SELinux, LVM, systemd, הרשאות מיוחדות ועוד), לא רק שינון. בחרו תשובה ותקבלו מיד משוב עם הסבר מפורט.

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>1. שירות Apache לא מצליח לגשת לקבצים בתיקייה <code>/web/data</code> למרות שהרשאות ה-Unix (<code>rwx</code>) תקינות לחלוטין ו-SELinux נמצא במצב <code>Enforcing</code>. מה הפעולה הנכונה ביותר לתיקון קבוע ועקבי אחרי reboot?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. להעביר את SELinux למצב <code>Permissive</code> לצמיתות כדי שהבעיה תיפסק</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. להריץ <code>chmod 777</code> על התיקייה כדי לפתור את בעיית ההרשאות</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. להגדיר עם <code>semanage fcontext -a -t httpd_sys_content_t "/web/data(/.*)?"</code> ואז להריץ <code>restorecon -Rv /web/data</code> כדי לתקן את ה-context באופן קבוע</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. להריץ פעם אחת <code>chcon -t httpd_sys_content_t /web/data</code> ולסיים, בלי צורך בשום פקודה נוספת</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> כשקובץ נוצר במיקום לא סטנדרטי (כמו <code>/web/data</code> במקום <code>/var/www/html</code>), הוא יורש context שגוי מהתיקייה שסביבו ולא את ה-context שהשירות מצפה לו. הפתרון הנכון והעמיד לאורך זמן הוא להוסיף כלל קבוע למסד המדיניות עם <code>semanage fcontext</code>, ואז להריץ <code>restorecon</code> כדי להחיל את הכלל בפועל על הקבצים הקיימים. <code>chcon</code> משנה context באופן נקודתי אך זמני בלבד - הרצת <code>restorecon</code> בעתיד (או relabel) תחזיר את הקבצים ל-context שמוגדר במסד המדיניות אם לא עדכנתם אותו עם <code>semanage</code>. מעבר ל-<code>Permissive</code> או <code>chmod 777</code> הם פתרונות שמבטלים את ההגנה במקום לתקן את הבעיה האמיתית.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>2. ל-Volume Group בשם <code>vg_data</code> אין כלל מרחב פנוי (Free PE), וברצונכם להרחיב Logical Volume קיים בו. מה חייב לקרות לפני שההרחבה תצליח?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין צורך בכלום - <code>lvextend</code> יכול להרחיב LV גם כשאין מרחב פנוי ב-VG, כי הוא לוקח את השטח ישירות מהדיסק הפיזי</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. צריך קודם להוסיף Physical Volume נוסף ל-VG (<code>vgextend</code>) או לשחרר PE פנויים מ-LV אחר, כדי שיהיה ל-VG מרחב פנוי לפני שאפשר להריץ <code>lvextend</code> בהצלחה</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. צריך למחוק את ה-VG כולו ולבנות אותו מחדש בגודל הרצוי</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. צריך להריץ קודם <code>resize2fs</code> או <code>xfs_growfs</code> על מערכת הקבצים - זה מרחיב אוטומטית גם את ה-VG</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ההיררכיה ב-LVM היא Physical Volume (PV) &rarr; Volume Group (VG) &rarr; Logical Volume (LV). <code>lvextend</code> יכול להקצות ל-LV רק מתוך מרחב פנוי שכבר קיים ב-VG שלו. אם אין מרחב פנוי ב-VG, חובה קודם להגדיל אותו - למשל בהוספת דיסק/פרטישן חדש כ-PV והרצת <code>vgextend</code>, או בצמצום LV אחר כדי לשחרר PE. רק אחרי שיש מרחב פנוי ב-VG אפשר להריץ <code>lvextend</code> על ה-LV, ואז בנפרד להרחיב את מערכת הקבצים עצמה עם <code>resize2fs</code> (ext4) או <code>xfs_growfs</code> (XFS) - הרחבת מערכת הקבצים היא שלב נפרד ולא קורית אוטומטית.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>3. מה בדיוק ההבדל בין <code>systemctl enable httpd</code> ל-<code>systemctl start httpd</code>?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. שתי הפקודות זהות לחלוטין - כל אחת מהן גם מפעילה את השירות מיד וגם דואגת שיעלה ב-boot הבא</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. <code>enable</code> יוצר קישור סימבולי ב-target המתאים כך שהשירות יעלה אוטומטית בכל boot עתידי, אך לא מפעיל אותו כעת; <code>start</code> מפעיל את השירות מיד ברגע הנוכחי, אך לא משפיע על מה שיקרה ב-boot הבא</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. <code>start</code> משפיע רק על boot עתידי, ו-<code>enable</code> מפעיל את השירות מיד</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>enable</code> משמש רק לשירותי systemd מסוג <code>oneshot</code>, ו-<code>start</code> לכל השאר</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> זו אחת הטעויות הנפוצות ביותר במבחן - <code>enable</code> ו-<code>start</code> הן שתי פעולות בלתי-תלויות לגמרי. <code>enable</code> רק יוצר קישורים סימבוליים בתיקיית ה-<code>.wants</code> של ה-target הרלוונטי (למשל <code>multi-user.target.wants</code>), כך שה-unit יופעל אוטומטית ב-boot הבא, אך אינו נוגע במצב הריצה הנוכחי. <code>start</code> מפעיל את השירות עכשיו, אך אם לא הרצתם גם <code>enable</code> הוא לא יעלה שוב אחרי reboot. לכן בפרקטיקה נהוג להריץ את שתיהן יחד, או להשתמש בקיצור <code>systemctl enable --now httpd</code>.</div>
</div>

<div class="quiz-card" data-answer="ד">
  <p class="quiz-question"><strong>4. תיקיית <code>/tmp</code> נגישה לכתיבה על ידי כל המשתמשים במערכת. איזו הרשאה מיוחדת מגדירה שכל משתמש יכול ליצור קבצים בתיקייה, אך רק הבעלים של קובץ מסוים (או root) יכול למחוק או לשנות שם לקובץ שלו, גם אם למשתמשים אחרים יש הרשאת כתיבה לתיקייה?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. SUID (Set User ID) - כאשר קובץ הרצה מופעל, הוא רץ תחת זהות הבעלים של הקובץ ולא תחת זהות המריץ</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. SGID (Set Group ID) על קובץ הרצה - הוא רץ תחת זהות הקבוצה הבעלים של הקובץ</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. SGID על תיקייה - קבצים חדשים שנוצרים בתוכה יורשים את קבוצת התיקייה במקום את הקבוצה הראשית של היוצר</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. Sticky Bit - כפי שמוגדר בפועל על <code>/tmp</code> (הרשאות <code>1777</code>), הוא מגביל מחיקה/שינוי שם של קובץ בתיקייה משותפת-כתיבה רק לבעלים של הקובץ, לבעלים של התיקייה, או ל-root</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ה-Sticky Bit (מסומן כ-<code>t</code> בסוף מחרוזת ההרשאות, ומתווסף כ-<code>1</code> בספרה הרביעית של המצב המספרי, כמו <code>1777</code>) הוא הרשאת ההגנה הקלאסית על תיקיות משותפות-כתיבה כמו <code>/tmp</code>. הוא לא מונע מאף אחד ליצור קבצים בתיקייה, אלא רק מגביל <strong>מי יכול למחוק/לשנות שם</strong> לקובץ קיים בתוכה - רק הבעלים של הקובץ עצמו, בעלי התיקייה, או root. חשוב להבדיל: SUID משפיע על תהליכים בזמן הרצה (למשל <code>passwd</code>), SGID על קובץ הרצה משפיע על זהות הקבוצה בזמן ריצה, ו-SGID על תיקייה משפיע על ירושת קבוצה של קבצים חדשים - כל אחד ממקרי שימוש שונה לגמרי מזה של Sticky Bit.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>5. מהו ההבדל המהותי בין <code>/etc/passwd</code> ל-<code>/etc/shadow</code>?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. <code>/etc/passwd</code> מיועד רק למשתמשי system, ו-<code>/etc/shadow</code> רק למשתמשים רגילים</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. <code>/etc/passwd</code> קריא לכל המשתמשים במערכת ומכיל פרטי חשבון כלליים (UID, GID, home, shell) ללא סיסמאות עצמן; <code>/etc/shadow</code> קריא רק ל-root ומכיל את ה-hash של הסיסמה יחד עם מדיניות תפוגה (aging)</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. שני הקבצים מכילים בדיוק את אותו מידע, ומוחזקים כגיבוי אחד לשני</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. <code>/etc/shadow</code> הוחלף לחלוטין ואינו קיים יותר בגרסאות עדכניות של RHEL</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> בעבר ה-hash של הסיסמה נשמר ישירות ב-<code>/etc/passwd</code>, אך מכיוון שהקובץ הזה חייב להיות קריא לכולם (תוכניות רבות צריכות למפות UID לשם משתמש), זה היווה סיכון אבטחה חמור. לכן ה-hash הועבר ל-<code>/etc/shadow</code>, קובץ שקריא אך ורק ל-root (הרשאות <code>000</code> או <code>600</code> בבעלות root). <code>/etc/passwd</code> ממשיך להכיל שדות כמו UID, GID ראשי, תיקיית בית ו-shell, בעוד שדה הסיסמה בו מכיל רק <code>x</code> שמסמן "עיין ב-shadow". חשוב גם לזכור: UID של משתמשי system הוא בדרך כלל מתחת ל-1000 (לרוב 0-999), ומשתמשים רגילים מתחילים מ-1000 ומעלה (ב-RHEL/CentOS מודרניים).</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>6. הוספתם כלל חדש עם <code>firewall-cmd --permanent --add-service=https</code>. מדוע גישה ל-HTTPS עדיין לא עובדת מיד לאחר הפקודה, ומה הפתרון?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. הדגל <code>--permanent</code> שגוי - צריך להריץ את הפקודה בלעדיו כדי שהיא תעבוד בכלל</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. יש להפעיל מחדש את כל השרת (reboot) כדי שכל שינוי ב-firewalld ייכנס לתוקף</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. <code>--permanent</code> שומר את הכלל בקונפיגורציה הקבועה (שנטענת מחדש רק ב-daemon start), אך לא משפיע על ה-runtime configuration הפעילה כרגע; יש להריץ <code>firewall-cmd --reload</code> כדי לטעון את הקבוע לתוך ה-runtime, או להוסיף את הכלל גם בלי <code>--permanent</code> להשפעה מיידית</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. שירות HTTPS חייב תמיד zone נפרד משירותי HTTP, ולכן חובה להגדיר zone חדש</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> ב-firewalld יש שתי שכבות קונפיגורציה נפרדות: ה-runtime configuration (המצב הפעיל כרגע בזיכרון) וה-permanent configuration (הנשמרת לדיסק ונטענת רק כש-firewalld עולה או כשמריצים <code>--reload</code>). כלל שנוסף עם <code>--permanent</code> נכתב לקונפיגורציה הקבועה בלבד ולא משפיע על התעבורה החיה כרגע. כדי שהשינוי ייכנס לתוקף מיידי בלי לאבד אותו אחרי reboot, יש להריץ <code>firewall-cmd --reload</code> שמסנכרן את ה-runtime עם הקובץ הקבוע. חלופה למבחנים: להריץ את אותה פקודה גם בלי <code>--permanent</code> להשפעה מיידית, וגם עם <code>--permanent</code> להתמדה אחרי reboot.</div>
</div>

<div class="quiz-card" data-answer="ב">
  <p class="quiz-question"><strong>7. מהו ההבדל בין קובץ ב-<code>crontab -e</code> של משתמש רגיל לבין קובץ שמוגדר תחת <code>/etc/cron.d/</code>?</strong></p>
  <div class="quiz-options">
    <button class="quiz-option" type="button" data-choice="א">א. אין שום הבדל מבחינת תחביר או הרשאות - שני הסוגים זהים לחלוטין</button>
    <button class="quiz-option" type="button" data-choice="ב">ב. ב-crontab של משתמש כל שורה מכילה 5 שדות זמן ולאחריהם הפקודה בלבד (הזהות רצה תמיד תחת בעל ה-crontab), בעוד שקובץ תחת <code>/etc/cron.d/</code> מוסיף שדה נוסף - שם המשתמש שתחתיו תרוץ הפקודה - בין שדות הזמן לפקודה עצמה</button>
    <button class="quiz-option" type="button" data-choice="ג">ג. קבצים תחת <code>/etc/cron.d/</code> תומכים רק בהרצה חד-פעמית (at), ולא בהרצה מחזורית</button>
    <button class="quiz-option" type="button" data-choice="ד">ד. crontab של משתמש תומך ב-6 שדות זמן, בעוד <code>/etc/cron.d/</code> תומך רק ב-4</button>
  </div>
  <div class="quiz-result" aria-live="polite"></div>
  <div class="quiz-explain"><strong>הסבר:</strong> תחביר 5 השדות (דקה, שעה, יום-בחודש, חודש, יום-בשבוע) משותף לשני הסוגים. ההבדל המהותי הוא זהות ההרצה: ב-crontab אישי (שנערך עם <code>crontab -e</code> ונשמר תחת <code>/var/spool/cron/</code>) המשימה תמיד רצה תחת המשתמש הבעלים של אותו crontab, ולכן אין צורך לציין שם משתמש בשורה. לעומת זאת, קבצים תחת <code>/etc/cron.d/</code> (בדיוק כמו <code>/etc/crontab</code> עצמו) מיועדים לשימוש על ידי root או חבילות מערכת, ולכן דורשים שדה נוסף בין שדות הזמן לפקודה - שם המשתמש שתחתיו תרוץ הפקודה - כדי לאפשר הרצת משימות עבור משתמשים שונים מתוך קובץ יחיד.</div>
</div>

<div class="quiz-card" data-answer="ג">
  <p class="quiz-question"><strong>8. הגדרתם למשתמש עם <code>edquota</code> soft limit של 500MB ו-hard limit של 600MB על נפח אחסון. מה קורה כשהמשתמש חוצה את ה-soft limit אך נשאר מתחת ל-hard limit, ולמה נדרש <code>quotacheck</code> לפני שהכל עובד?</strong></p>
  <div class="quiz-options">

    <button class="quiz-option" type="button" data-choice="ב">ב. חציית soft limit לא עושה דבר בכלל - היא קוסמטית בלבד ואינה משפיעה על המשתמש אי-פעם</button>

<script>
(function () {
  function initQuiz() {
    var cards = document.querySelectorAll('.quiz-card');
    var scoreEl = document.getElementById('quiz-score');
    var resetAllBtn = document.getElementById('quiz-reset-all');

    function updateScore() {
      if (!scoreEl) return;
      var correctCount = document.querySelectorAll('.quiz-card--answered[data-was-correct="true"]').length;
      scoreEl.textContent = 'ענית נכון על ' + correctCount + ' מתוך ' + cards.length;
    }

    function answerCard(card, chosenBtn) {
      var correct = card.getAttribute('data-answer');
      var chosen = chosenBtn.getAttribute('data-choice');
      var isCorrect = chosen === correct;

      card.classList.add('quiz-card--answered');
      card.setAttribute('data-was-correct', isCorrect ? 'true' : 'false');

      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = true;
        if (opt.getAttribute('data-choice') === correct) {
          opt.classList.add('quiz-option--correct');
        } else if (opt === chosenBtn) {
          opt.classList.add('quiz-option--incorrect');
        }
      });

      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = isCorrect ? '✅ נכון!' : '❌ לא נכון - התשובה הנכונה מסומנת בירוק.';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
        result.classList.add(isCorrect ? 'quiz-result--correct' : 'quiz-result--incorrect');
      }

      updateScore();
    }

    function resetCard(card) {
      card.classList.remove('quiz-card--answered');
      card.removeAttribute('data-was-correct');
      var options = card.querySelectorAll('.quiz-option');
      options.forEach(function (opt) {
        opt.disabled = false;
        opt.classList.remove('quiz-option--correct', 'quiz-option--incorrect');
      });
      var result = card.querySelector('.quiz-result');
      if (result) {
        result.textContent = '';
        result.classList.remove('quiz-result--correct', 'quiz-result--incorrect');
      }
    }

    cards.forEach(function (card) {
      card.querySelectorAll('.quiz-option').forEach(function (btn) {
        btn.addEventListener('click', function () {
          if (card.classList.contains('quiz-card--answered')) return;
          answerCard(card, btn);
        });
      });
    });

    if (resetAllBtn) {
      resetAllBtn.addEventListener('click', function () {
        cards.forEach(resetCard);
        updateScore();
      });
    }

    updateScore();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initQuiz);
  } else {
    initQuiz();
  }
})();
</script>
